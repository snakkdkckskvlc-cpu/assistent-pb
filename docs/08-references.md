# Референс-проекты

Пять open-source проектов, изучаемые в контексте «Ассистента ПБ». Локально
лежат в `references/` (не в git — большие). Здесь только карточки: что взяли
и почему. Обновлено после глубинного код-ревью каждого проекта (2026-07-16) —
см. `README_reference.md` в каждом подкаталоге для полных находок.

## Как их читать

- **Не копируем код** — берём паттерны, данные-схемы, UX-решения.
- Каждый архив в `references/<project>/` содержит `README_reference.md`
  с нашей записью «что применимо / что нет».
- **Важно**: некоторые из этих проектов сильно изменились с момента, когда
  писались первые заметки (см. пункты 3 и 4) — актуальное состояние кода
  проверено заново, старые карточки местами были неверны.

## 1. gpt4all — UX/UI reference for the project

Ссылка: https://github.com/nomic-ai/gpt4all · Лицензия: MIT (подтверждено:
gpt4all-chat, gpt4all-backend, gpt4all-bindings/python — все MIT)

**Поправка**: чат — это чистый Qt/QML (`gpt4all-chat/qml/*.qml`), **не**
Qt+WebEngine — HTML/JS там нет вообще. Значит, брать можно только паттерн
поведения, переписывая с нуля на vanilla JS/CSS, а не «портировать» что-то.

Референс десктоп-чата с локальной моделью. Конкретные паттерны (ранжировано
по ценности, детали и файлы — в `README_reference.md`): send/stop-кнопка
по состоянию задачи; granular статус-текст вместо одного «Обработка…»;
combo-box, совмещённый с прогресс-баром/статусом модели; toast-уведомления
(сами MIT, с открытым источником в комментарии); коллапс-панель источников;
двухуровневые настройки со скрытием пустых табов; семантические цвета через
CSS-переменные (валидирует наш план, не учит новому); `fontScale`-подобный
общий UI-масштаб (не только текст) — стоит рассмотреть для пользователей
постарше. Стриминг ответа реализован через Qt-сигналы + полный re-parse
markdown на каждый токен (не инкрементально) — обнадёживающий прецедент:
наш план «перезапускать marked.js на каждый чанк» не будет недоработкой,
это стандартный подход. Для нас стриминг = изменения и на бэкенде
(`infrastructure/llm.py` сейчас жёстко `"stream": False`), и на фронте
(`app.js::pollTask` — сейчас поллинг раз в 1.5с одного JSON, а не SSE) —
ценно для восприятия скорости, но не критично, пока фичи не диалоговые.

## 2. docquery — Answer extraction from scans and PDFs

Ссылка: https://github.com/impira/docquery · Лицензия: MIT (модель
`impira/layoutlm-document-qa` — тоже MIT, это единственная MIT-версия в
семействе LayoutLM; LayoutLMv2/v3 и мультиязычный LayoutXLM — **некоммерческая
CC-BY-NC-SA-4.0**, не использовать при любом соблазне «взять мультиязычную
версию для русского»).

**Вердикт: не запускать их модель.** Токенизатор — английский BERT-uncased,
на русских договорах будет разваливаться на UNK-сабтокены; DOCX не
поддерживается вообще (только PDF/image/HTML). DocQuery сам не поддерживается
(README: "not actively maintained").

**Что реально берём**: идею «вопросы = схема извлечения полей» — но через
уже работающий `llm.chat_json` (Ollama JSON-mode), а не их модель. Один
промпт-проход извлекает номер договора/дату/стороны/сумму как структурные
поля, дополняя (не заменяя) уже существующую свободную JSON-схему находок
в `legal.txt`. Также: `pytesseract.image_to_data()` вместо
`image_to_string()` в `infrastructure/parsers/ocr.py` даёт confidence по
словам бесплатно (тот же уже установленный pytesseract) — можно показывать
«скан низкого качества» вместо тихой деградации. И: `pdf_parser.py` уже
использует `pdfplumber`, но выкидывает координаты слов, которые
`extract_words()` того же объекта отдаёт бесплатно (для будущего «прыгнуть
к пункту в PDF»).

## 3. OpenContracts — Deep legal contract analysis

Ссылка: https://github.com/JSv4/OpenContracts · Лицензия: **MIT**
(поправка: раньше числилась Apache-2.0 — в текущем чекауте `LICENSE` и
README однозначно MIT).

**Поправка**: проект сильно вырос — это уже не «аннотатор пунктов
договора», а «programmable citation graph»: агентный фреймворк (PydanticAI),
MCP-сервер, права доступа, голосование/бейджи. Нет классов `Section`/
`Clause` — вместо них единый self-nesting `Annotation` + `AnnotationLabel`
(таксономия — юзер/аналайзер-редактируемая, не фиксированный enum и не
ML-классификатор) + отдельная параллельная система `Extract`/`Column`/
`Datacell` для структурного извлечения (ближе к нашему кейсу «одна риск-
находка = одна строка», чем `Annotation`). Авторы сами отмечают в докстринге
`Analysis`, что `Analysis` и `Extract` дублируют друг друга и это
нерешённый техдолг — хороший повод не повторить их ошибку у себя.

**Право-размерная (не «как у них») цель для Sprint 5+**: 3 плоские таблицы
в существующей `infrastructure/db.py` — `contracts` (+ content-hash для
версионности, 2 колонки, без полного dual-tree версионирования),
`analyses` (без Celery/Guardian-прав), `findings` (плоская таксономия вместо
`LabelSet`). Отдельно, **самая дешёвая находка всего ревью**: паттерн
`is_grounding_source` — просить LLM возвращать точную цитату при каждой
находке, затем substring-поиском подсвечивать её в оригинальном тексте
договора. Не требует новых таблиц, только правка промпта + один валидатор.

**Явно не берём** (диспропорционально нашему масштабу): полное dual-tree
версионирование папок/корзины (1000+ строк), Guardian-права по объектам
(мы single-tenant), Celery chord/group параллелизм (нечего фанаутить на
одном воркере), плагинный реестр анализаторов.

## 4. private-gpt — Local RAG assistant for documents

Ссылка: https://github.com/zylon-ai/private-gpt (переехал с imartinez) ·
Лицензия: Apache-2.0.

**Важная поправка**: локальная копия — это `v1.0.1`, «PrivateGPT revamp»
(апрель 2026, #2230, breaking changes). Проект, который описывали старые
заметки (LangChain, `LOADER_MAPPING`, локальные HuggingFace-эмбеддинги,
Chroma), **в этом чекауте не существует** — LangChain выпилен, локальных
эмбеддингов больше нет (только OpenAI-совместимый эндпоинт, т.е. Ollama
через его OpenAI-compat API), Chroma не поддерживается (только Qdrant),
вместо простой структуры — DI-контейнер (`injector`) и ~35 компонентов
(MCP, sandboxed code exec, SQL-агент, S3/SMB, две очереди задач). По факту
наш текущий стек (in-process эмбеддинги, ChromaDB) сейчас **ближе** к тому,
чем private-gpt был раньше, чем к тому, чем он стал. Как архитектурный
шаблон для «идеальной структуры» этот чекаут не подходит — не гнаться.

**Что реально берём** (алгоритмы, не их DI/registry-обвязку):
1. **Grounded-цитирование** — самая ценная находка: каждому RAG-чанку
   присваивается короткий ID, LLM просят цитировать `[ID]` рядом с
   утверждением, затем **ID сверяется с реально отданными в контекст
   чанками** — заявленная, но не подтверждённая цитата отбрасывается, а не
   доверяется на слово. У нас `_rag_sources` в `run_legal_analysis`
   (`pipelines/legacy.py`) сейчас — это просто список источников, которые
   были в контексте, без проверки, что конкретная находка реально на них
   опирается. Порт — правка JSON-схемы + один валидатор, без llama-index.
2. **Sentence-aware chunking** — их алгоритм (не NodeParser-обвязка):
   сначала бьём на предложения, только «слишком длинные» предложения режем
   дальше по токенам. У нас `_chunk_by_words`/`_chunk_text`
   (`pipelines/legacy.py`, `packages/rag/.../indexer.py`) режут по словам
   без учёта границ предложений вообще. Для русского — явно
   `nltk.sent_tokenize(text, language="russian")` (не тот
   непроинициализированный Punkt, что использует сам private-gpt) или
   regex-сплиттер под русские сокращения («п.», «ст.», «т.д.»).
3. **Settings** — их ручной YAML+профили — оверкилл, но лёгкий
   `pydantic.BaseModel`/`pydantic-settings` вместо плоских
   `os.environ.get()` в `config.py` — валидация и дефолты почти бесплатно
   (pydantic уже транзитивная зависимость FastAPI).

**Не берём**: ingestion-пайплайн целиком (тянет torch/vision-модели/внешний
Docling-сервис ради форматов, которые нам не нужны), DI-контейнер, дуальные
очереди задач (arq+Celery) — это инфраструктура многопользовательского
SaaS, а не одного локального сервера.

## 5. languagetool — Offline spelling, grammar and style check for Russian

Ссылка: https://github.com/languagetool-org/languagetool · Лицензия:
LGPL-2.1 (core/ru/server — идентично; единственный GPL-модуль во всём
дереве — ирландский словарь, нам не нужен).

**LGPL и наш кейс — чисто**: обязательства LGPL — про *линковку*, не про
вызов по HTTP отдельного процесса. Запуск `languagetool-server.jar` как
sidecar-процесса на 8081 и обращение к нему через `httpx` — это не
линковка (как вызов любого другого сетевого сервиса), обязательств не
возникает даже при гипотетической дистрибуции. Сервер-мод реальный и
именно такой, как предполагалось: `java -jar languagetool-server.jar
--port 8081`, `POST /v2/check` (form-encoded вход, JSON выход), биндится
только на localhost по умолчанию.

**Покрытие русского — реально тоньше, чем английского, с цифрами**: 119
правил + 166 групп правил для `ru` против ~1700+960 для `en` (~10-15×
разрыв, подтверждено подсчётом). Словарь орфографии есть (Hunspell FSA,
включая ё-вариант), false-friends для ru↔en/de/pl тоже есть. Но
`RussianConfusionProbabilityRule` — рабочий код с файлом данных всего на
5 строк, то есть механизм есть, а данных под него почти нет.

**Поправка/ловушка**: `/v2/words/add` (HTTP API для юзер-словаря) —
**тупиковый путь**, завязан на облачную БД аккаунтов, без БД всегда пустой.
Реальный механизм — плоский текстовый файл `spelling_global.txt` на
classpath (уже используется в реальном `ru/hunspell/spelling.txt` для
похожего класса терминов — ГАПОУ, ГИБДД, ГЛОНАСС), без пересборки, работает
после рестарта.

**Рекомендация по очерёдности** (не «давайте сразу гибрид»): сначала —
глоссарий пожарных терминов + инструкция «сообщай только при высокой
уверенности» прямо в промпте `spellcheck.txt` (правка на день, ноль новой
инфраструктуры), измерить эффект на реальных false positives, и только
потом решать, нужен ли LanguageTool как второй, детерминированный проход
(своя JVM, свой порт, ещё один процесс на сервере компании — не бесплатно
по эксплуатации). Если глоссарий закроет большую часть проблемы —
LanguageTool может не понадобиться вовсе.

## Дерево локальных копий (не в git)

```
references/
├── gpt4all-main/           # 34 МБ распакованных
├── docquery-main/          # 44 КБ
├── OpenContracts-main/     # 89 МБ
├── private-gpt-main/       # 25 МБ
└── languagetool-master/    # 98 МБ (~ 300 МБ распакованных)
```

Общий объём ~450 МБ распакованных исходников. Каталог `references/` целиком
в `.gitignore` — на GitHub идёт только этот файл.

Как обновить копии:
1. Скачать свежий zip с GitHub оригинала.
2. Распаковать в `references/<project>-main/`.
3. Дополнить `README_reference.md` в подкаталоге, если появилось что-то
   новое интересное. **Проверять актуальность старых заметок** — минимум
   2 из 5 проектов (OpenContracts, private-gpt) успели радикально
   измениться между записью заметок и этим ревью.

## Сводный план по приоритетам (после ревью 2026-07-16)

Полный ранжированный список с обоснованием — в ответе сессии; здесь только
маршрут:

- **Уровень 1 (дёшево, без новой инфры)**: глоссарий в промпт spellcheck;
  `image_to_data` вместо `image_to_string` в OCR; извлечение структурных
  полей договора через `chat_json`; grounded-цитирование в юр. анализе;
  quote-anchoring для находок; sentence-aware chunking.
- **Уровень 2 (умеренно)**: 3 SQLite-таблицы для истории анализов;
  pydantic-настройки вместо `os.environ.get()`; UI-паттерны из gpt4all
  (статус-текст, toast, коллапс-источники).
- **Уровень 3 (крупные решения, нужен отдельный go/no-go)**: LanguageTool
  как sidecar (после, не вместо, промпт-фикса); стриминг ответа LLM;
  таксономия находок как редактируемая таблица.
- **Не делаем**: полный data-модель/permissions/versioning OpenContracts;
  архитектура private-gpt v1.0.1 целиком; модель DocQuery в проде;
  копирование UI-кода gpt4all (там нет HTML/JS — копировать нечего).

# Перенос на сервер: задача второму разработчику

## Цель

Приложение работает **на одном сервере компании**. Сотрудники открывают его с
любого компьютера в сети браузером. Вычисления (LLM, OCR, поиск по нормативке)
идут **на сервере**, на компьютерах не выполняется ничего.

## Как сейчас и как должно стать

| | сейчас | нужно |
|---|---|---|
| Установка | на каждый компьютер | один сервер |
| Запуск | окно pywebview + локальный uvicorn на 127.0.0.1 | uvicorn на 0.0.0.0, клиент — браузер |
| Ollama / LanguageTool / ChromaDB | на каждом компьютере | только на сервере |
| Нормативный корпус | копия у каждого | один на всех |
| Пользователей одновременно | 1 | N |

Сервер: Ryzen 5 5600, 128 ГБ RAM, без GPU.

---

## Что было сделано по этому брифу

Все шесть блокеров закрыты — ниже с указанием, чем именно, чтобы было видно,
где искать при разборе:

| блокер | закрыт |
|---|---|
| Авторизации не было | вход по логину и паролю, сессии, защита всех роутеров |
| Каждый видел чужие документы | изоляция по владельцу: документы, задачи, история |
| Очередь на один воркер молча копила ожидание | показ позиции в очереди и оценки времени |
| Задачи жили только в памяти процесса | результаты переживают перезапуск сервера |
| Одинаковые имена файлов затирали друг друга | уникальные имена при загрузке |
| Привязка к localhost | серверный режим запуска (`scripts/run_server.py`) |

Сверх брифа сделано: запрет выхода в интернет (кроме localhost), контроль
целостности кода при запуске, шифрование документов на диске через DPAPI,
запрет записи вне рабочей папки.

**Остаётся справедливым:** uvicorn запускать с ОДНИМ воркером. Очередь живёт в
памяти процесса, и при `--workers 2` запрос `GET /api/tasks/{id}` уйдёт в
другой процесс и вернёт 404.

## Что уже готово — не трогать

- **Скачивание в браузере работает.** `app.js::downloadFile` имеет фолбэк на
  `<a download>`; мост `window.pywebview.api` нужен только десктопной версии,
  в браузере ветка не выполняется.
- **Фронтенд отдаёт сам бэкенд** (`views/static_pages.py`). Отдельный
  веб-сервер под статику не нужен, nginx — только как обратный прокси и точка
  авторизации.
- **Размер окна модели подбирается по памяти сам** (`config._auto_num_ctx_legal`).
  На 128 ГБ выберет 32768: договор уйдёт одним запросом вместо десяти частей —
  генерации примерно вдесятеро меньше. Ничего настраивать не нужно;
  перекрывается переменной `LLM_NUM_CTX_LEGAL`, если понадобится.
- **ChromaDB и SQLite — просто файлы** в `data/`. Отдельные серверы БД не нужны.

## Модель

На сервер ставится **qwen3:30b-a3b** — 30 млрд параметров, но архитектура MoE:
активны только 3 млрд на токен. На CPU это единственный способ получить
большую модель без потери скорости; плотная модель того же размера считала бы
договор около получаса.

```
ollama pull qwen3:30b-a3b
echo qwen3:30b-a3b > data\llm_model.txt
```

Файл `data/llm_model.txt` — то, откуда приложение берёт имя модели
(`config._default_llm_model`). Без него останется qwen2.5:7b-instruct.

**Проверка после установки:** откройте `/api/health`. Если ОЗУ не хватает,
там будет предупреждение с цифрами — модель весит 18,6 ГБ, и на машине
меньше ~26 ГБ она уйдёт в swap. Симптом нехватки памяти не ошибка, а
бесконечное ожидание, поэтому проверять надо до того, как этим начнут
пользоваться.

Замерять качество имеет смысл там же, на сервере:

```
python scripts/evaluate_prompts.py            # 40 размеченных рисков
python scripts/evaluate_prompts.py --bare     # для сравнения: без обвязки
```

Эталон на 7B: precision 0.645, recall 0.50, красные риски 16 из 23.

## Сервисы на сервере

| сервис | порт | запуск |
|---|---|---|
| Ollama | 11434 | системный сервис |
| LanguageTool | 8081 | `tools/languagetool/start.sh` |
| Бэкенд | 8000 | uvicorn, 1 воркер |

Все три должны стартовать автоматически (systemd) и переживать перезагрузку.
Наружу из компании **ничего не публиковать** — только внутренняя сеть:
приложение работает офлайн by design, интернет ему не нужен.

## Данные

`data/` — единственный каталог с состоянием, его и бэкапить:

| | что |
|---|---|
| `data/chroma/` | индекс нормативки (~3300 фрагментов) |
| `data/app.db` | справочник адресатов, история, отзывы |
| `data/uploads/`, `data/outputs/` | документы пользователей |

После первого развёртывания прогнать индексацию:

```
python scripts/index_corpus.py            # нормативка РФ
python scripts/index_corpus.py --domain nlmk   # документы НЛМК, когда загружены
python scripts/check_corpus.py            # проверка целостности
```

## Приёмка

- [ ] С двух разных компьютеров открывается, обе сессии работают
- [ ] Второй пользователь видит очередь, а не ошибку
- [ ] Одинаково названные файлы от двух людей не перетирают друг друга
- [ ] Перезапуск сервера не роняет приложение (systemd поднимает)
- [ ] Без авторизации приложение недоступно
- [ ] Скачивание DOCX работает из браузера
- [ ] `/api/health` отвечает: Ollama и LanguageTool видны
- [ ] Юр-анализ договора на 17 страниц укладывается в одну часть (в логе
      «1 част(и/ей)») — значит окно подобралось правильно

## Что решить до начала

1. **Авторизация** — basic auth, AD или ограничение по IP?
2. **Очередь** — последовательно с показом позиции или параллельно?
3. **Устойчивость** — допустимо ли терять незавершённые задачи при
   перезапуске? Если нет, задачи переносить в SQLite.

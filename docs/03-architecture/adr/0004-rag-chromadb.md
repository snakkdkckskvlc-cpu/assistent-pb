# ADR-0004 · RAG на ChromaDB и multilingual-e5-large

**Дата**: 2026-07-14 · **Статус**: принято

## Контекст

Юридический анализ договора требует **ссылок на конкретные статьи ФЗ, ГК,
СП**. Модель без подсказок галлюцинирует — придумывает несуществующие
номера статей. Решение — RAG: индексируем корпус нормативки, при анализе
подтягиваем 5–6 релевантных чанков в промпт.

Требования:
- Работает офлайн, embedded (без отдельного сервиса).
- Поддерживает русский язык.
- Индекс на 10–100 тыс. чанков (весь ГК + ФЗ + СП + ГОСТ).
- Быстрый top-k поиск (< 500 мс на запрос).

## Решение

**Векторная БД**: [ChromaDB](https://www.trychroma.com/) в embedded-режиме.
Хранит индекс в `data/chroma/` как файлы. Zero-config, one-line запрос.

**Эмбеддер**: `intfloat/multilingual-e5-large` (sentence-transformers,
~1.3 ГБ). Топ по русскому в бенчмарках MTEB на момент выбора.

**Чанкинг**: по 500 слов с перекрытием 50 (простой word-split, без сложной
семантики — для нормативных актов работает достаточно хорошо).

**Идемпотентность**: файлы индексируются по SHA-256 контента, повторный
запуск пропускает уже проиндексированные.

## Пересмотр 2026-07-29

Допущение «для нормативных актов работает достаточно хорошо» проверили на
живом индексе — оно неверно. Нарезка по счётчику слов не знает про границы
статей, и в один чанк на 4238 символов попадали **восемь разных статей ГК**
(309, 310, 328, 330, 333, 395, 401, 421). Модель получала простыню и для
неустойки 2 % в день сослалась на ст. 395 вместо верной ст. 333 — причём
ст. 395 в переданный контекст вообще не попадала.

Что изменено:

- **`chunk_by_articles`** — нарезка по границам `Статья N` / `Пункт N` /
  `N.N.N` для типов `federal_law`, `government_decree`, `sp`, `gost`, `code`.
  Чанк = одна статья, её номер уезжает в метаданное `article`. Для писем,
  договоров и документов без разметки остаётся `chunk_sentences`.
- **Префиксы e5** — `passage: ` при индексации, `query: ` при поиске. Модель
  `multilingual-e5-large` обучена с ними; раньше они не использовались вовсе.
  Менять только вместе с полной переиндексацией.
- **Метаданные до потребителя** — `Retriever` отдаёт `doc_type`,
  `act_number`, `article`, `effective_date`, `status`, а не только
  `{text, source, score}`.
- **Версионирование** — структурное поле `status` (`actual` | `superseded`) в
  `corpus/_meta.json`; отменённые редакции отсекаются фильтром по умолчанию.
- **Фильтр по типу документа** — после переиндексации 74 % корпуса стали
  техническими СП, и запрос про неустойку выдавал своды правил по отоплению.
  Юр-анализ теперь ищет нормы про санкции только среди `code`, `federal_law`,
  `government_decree`.

Масштаб индекса: было 8 файлов и 13 чанков (то самое MVP-состояние из раздела
«Последствия» ниже), стало 26 файлов и 3334 чанка.

**Отложено сознательно** (обсуждалось, не берём сейчас):

- *Гибридный поиск BM25 + вектора* — ценно и бьёт в реальную проблему («ст.
  333» это лексика, а не семантика), но сначала надо было починить чанкинг: на
  простынях из восьми статей BM25 дал бы то же размытое попадание. Вернуться
  после замеров на постатейном индексе.
- *Cross-encoder реранкинг* — боевой сервер без GPU, анализ договора и так
  идёт десятки минут. Реранк 20 кандидатов добавит минуты на каждую часть.
- *Отдельные коллекции под каждый домен* — корпус в десятки файлов, метаданные
  плюс `where=` дают то же самое без merge-логики и N round-trip'ов.
  Пересмотреть при >10 тыс. документов.
- *LLM-роутер выбора коллекции* — плюс 20–60 с на CPU за запрос ради выбора из
  двух вариантов. Заменён правилом по ключевым словам.
- *Масштаб до миллионов документов* — ChromaDB на SQLite этого не тянет, это
  другая БД (Qdrant/pgvector) и другой ADR. Реальный потолок здесь — тысячи.

## Альтернативы

1. **Qdrant / Milvus / Weaviate** — правильнее для кластера, но требует
   отдельный сервис. Отвергнуто для MVP.
2. **FAISS напрямую** — быстро, но без метаданных, HNSW настроек, TTL.
3. **Только keyword search (BM25)** — не понимает синонимов и переформулировок.
4. **Промпт-инъекция «пропиши всю нормативку»** — не влезет в контекст.

## Последствия

**Плюсы**:
- `chromadb.PersistentClient(path=...)` — одна строчка настройки.
- Быстрый первичный индекс: 84 KB корпуса → 13 чанков за 15 секунд.
- Поиск даёт релевантные ссылки: `ст. 401 ГК РФ`, `ст. 723 ГК РФ` — реальные
  статьи из проиндексированных файлов.

**Минусы**:
- Эмбед-модель весит 1.3 ГБ — качается при первой индексации.
- Sentence-transformers тянет torch (~200 МБ).
- При большом корпусе (100+ файлов) индексация занимает часы. Для
  MVP-корпуса (8 файлов) — минуты.

## Границы модуля

RAG вынесен в отдельный пакет `packages/rag` (`fire_safety_rag`):
- Не зависит от backend/frontend.
- Собственный `config.py` через env-vars.
- `text_reader` — параметр `build_index`, что позволяет расширить корпус
  сложными форматами (DOCX, PDF) без правки RAG-кода.

# ADR-0001 · Monorepo с apps/ и packages/

**Дата**: 2026-07-14 · **Статус**: принято

## Контекст

MVP Sprint 1 писался в плоской структуре: `backend/`, `frontend/`,
`scripts/`, `install/` в корне. При росте появились проблемы:
- Смешение уровней абстракции (переиспользуемая логика RAG соседствует с
  backend-специфичным кодом).
- Нет чёткого места для дополнительных приложений (CLI-утилиты, будущий
  веб-клиент, мобильная версия).
- Сложно версионировать компоненты отдельно.

## Решение

Переходим на monorepo с двумя корневыми группами:

- **`apps/`** — конечные приложения (то, что запускается пользователем):
  - `apps/backend/` — FastAPI-сервис.
  - `apps/desktop/` — pywebview-обёртка + фронтенд.
  - (в будущем) `apps/cli/`, `apps/mobile/`.
- **`packages/`** — переиспользуемая логика:
  - `packages/rag/` — RAG-модуль (`fire_safety_rag`), не зависит от backend.

Всё управляется через **[uv workspaces](https://docs.astral.sh/uv/concepts/workspaces/)**:
один корневой `pyproject.toml` с `[tool.uv.workspace]`, тонкие манифесты
в пакетах, единый lockfile.

## Альтернативы

1. **Оставить как есть** — плоская структура. Отвергнуто: не масштабируется,
   мешает переиспользовать RAG.
2. **`src/` layout без разбиения** (один пакет `fire_safety_assistant` с
   подпакетами). Отвергнуто: не даёт границ между слоями, тесты и
   зависимости смешиваются.
3. **Отдельные Git-репозитории** (backend, desktop, rag). Отвергнуто:
   слишком тяжело для команды из 1-2 человек, PR становятся многорепными.

## Последствия

**Плюсы**:
- Чёткие границы между приложениями и библиотеками.
- Легко вынести `packages/rag` в отдельный релиз при необходимости.
- Стандарт индустрии (Nx, Turborepo, Rush, uv workspaces).

**Минусы**:
- Требует `PYTHONPATH=apps/backend/src:packages/rag/src` при запуске без
  установки пакетов (решается либо `uv sync`, либо через `pip install -e`).
- Разработчику нужно понимать, где какой код лежит (mitigation: описано в
  `CONTRIBUTING.md`).

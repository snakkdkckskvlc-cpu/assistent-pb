# КАТАЛОГ ФУНКЦИЙ-ВДОХНОВЕНИЯ

**Пометки:** `[ЗАКОН]` — закрывает обязательное по закону, продаётся легче всего · `[ВЕЗДЕ]` — переиспользуется у любого клиента любой отрасли · `[ОТРАСЛЬ]` — под конкретную вертикаль · `[БЕЗ ИИ]` — работает без модели, значит быстро и не разочарует на CPU

**Если брать три — берите № 1, № 12, № 33.** Движок сроков окупается в каждой вертикали и не требует ни LLM, ни новых зависимостей; двухпанельный анализ договора превращает существующий юрблок в то, что видно на демо; экспорт конфигурации клиента спасает от 10 форков через год.

## РУКОВОДИТЕЛЮ

**1. «Что горит на этой неделе» — утренний список сроков** `[ВЕЗДЕ]` `[БЕЗ ИИ]`
Зачем: система сама приносит список истекающих инструктажей, поверок, перезарядок, договоров и отчётных дат, а не ждёт, когда о них вспомнят.
Подсмотрено: Khoj (агент срабатывает по расписанию и сам приносит результат, а не ждёт вопроса) + Paperless-ngx (триггер по значению пользовательского поля-даты) + 1С:Охрана труда (событие порождает срок).
Переиспользует: SQLite-справочники, очередь задач (ночной джоб), ванильный фронт. Трудоёмкость: неделя.
Это единственный блок, которого нет ни в одном виде и который окупается у каждого клиента.

**2. Одна таблица «документы × параметры» вместо 50 отчётов** `[ВЕЗДЕ]`
Зачем: после пакетной проверки руководитель получает не 50 файлов, а одну сетку «договор × сумма × срок × неустойка × автопролонгация» с кликом в место в документе и выгрузкой в XLSX.
Подсмотрено: OpenContracts (Extract-сетка: колонка = вопрос, ячейка = значение со ссылкой на аннотацию-источник).
Переиспользует: пакетная проверка, парсеры, классификатор документов, LLM с JSON-схемой. Трудоёмкость: неделя.

**3. «Где висит документ» — внутреннее визирование с историей** `[ВЕЗДЕ]`
Зачем: видно, у кого лежит договор, кто не завизировал и сколько дней уже.
Подсмотрено: Documenso (модель envelope → recipients с ролью и порядком → events) + Directum Lite.
Переиспользует: SQLite (2–3 таблицы), генератор DOCX для печати листа согласования. Трудоёмкость: месяц.
УКЭП не делать — это КриптоПро и отдельная история; внутреннее визирование с аудитом — делать.

**4. Экран «сетевая активность приложения: ноль»** `[ВЕЗДЕ]` `[БЕЗ ИИ]`
Зачем: превратить netguard из технической детали в проверяемое обещание, которое показывают на демо (вынуть кабель при работающей проверке договора).
Подсмотрено: PrivateGPT и GPT4All построили на этом всё позиционирование, но у них это маркетинг, а у него — запрет сети в коде.
Переиспользует: netguard, ванильный фронт. Трудоёмкость: день.

**5. Предполётная проверка железа при установке** `[ВЕЗДЕ]` `[БЕЗ ИИ]`
Зачем: снять единственный вопрос, на котором ломается сделка — «а не будет ли тормозить на нашем сервере».
Подсмотрено: LM Studio (светофор у каждой модели: влезет / не влезет в вашу память — пользователь не читает про Q4_K_M, он видит цвет).
Переиспользует: Ollama, SQLite (записать замер один раз при установке). Трудоёмкость: день.

**6. Отчёты под клиента без релиза** `[ВЕЗДЕ]` `[БЕЗ ИИ]`
Зачем: на внедрении руководитель просит «а покажите мне вот такой срез» — и срез появляется за 15 минут, а не в следующей версии.
Подсмотрено: Datasette canned queries (именованные SQL-запросы из конфига, из которых автоматически строится форма параметров и таблица результата).
Переиспользует: SQLite без ORM (прямые SQL), ванильный фронт. Трудоёмкость: день.

## БУХГАЛТЕРУ

**7. Штрихкод на печатной форме → подписанная бумага возвращается в базу одним сканом** `[ВЕЗДЕ]` `[БЕЗ ИИ]`
Зачем: пачка подписанных актов и путевых листов сканируется одним потоком и раскладывается по документам без ручного сопоставления.
Подсмотрено: Скан-Архив (привязка скана к документу учётной системы через штрихкод на бумаге).
Переиспользует: генератор DOCX и печатные формы (штрихкод печатается на них), парсеры. Трудоёмкость: неделя.
Очень эффектно на демо и стоит копейки: генерация штрихкода + pyzbar, тяжёлых зависимостей нет.

**8. Реестр документов с двусторонними связями** `[ВЕЗДЕ]`
Зачем: из карточки допсоглашения видно основной договор, из акта — договор и оплату; поиск «а где всё по этой сделке» перестаёт быть археологией.
Подсмотрено: Paperless-ngx (тип поля Document Link — двусторонняя ссылка между документами; плюс восемь типов пользовательских полей, включая «деньги» с валютой и «выбор из списка»).
Переиспользует: SQLite, классификатор документов (подставляет тип), парсеры. Трудоёмкость: месяц.
Это самый переиспользуемый модуль во всём каталоге: чертёж модели данных переносится на SQLite без ORM почти дословно.

**9. ИИ как вычисляемая колонка реестра** `[ВЕЗДЕ]`
Зачем: загрузил документ в реестр — колонки «тип», «контрагент», «сумма», «срок», «краткое содержание» заполнились сами, как формула в Excel; никто не «идёт в ИИ-раздел».
Подсмотрено: Airtable AI fields / Notion autofill (ИИ не функция, которую вызывают, а свойство таблицы; промпт хранится один раз у колонки).
Переиспользует: очередь задач, Ollama, классификатор документов. Трудоёмкость: неделя.
Для его модели это идеальный инструмент кастомизации: у нового клиента настройка = завести колонки с нужными промптами руками, при клиенте, без строчки кода.

**10. Шаблонный разбор узких типовых форм вместо полного OCR** `[ВЕЗДЕ]`
Зачем: счёт от постоянного контрагента, акт, путевой лист с фиксированной вёрсткой разбираются почти со 100% точностью, а кривые сканы честно уходят человеку.
Подсмотрено: Entera (30+ типов первички), но с сознательным сужением — полный OCR на Windows без GPU разочарует.
Переиспользует: парсеры, классификатор документов. Трудоёмкость: месяц.

**11. Календарь отчётных сроков** `[ЗАКОН]` `[ВЕЗДЕ]` `[БЕЗ ИИ]`
Зачем: кто что сдаёт и когда — декларации, ПЭК, 1-Т «условия труда», 7-травматизм, отчёт об отходах.
Подсмотрено: ниша вокруг «Модуля природопользователя» Росприроднадзора (сами формы государство раздаёт бесплатно и обновляет само — деньги там, где Модуль не помогает: не пропустить срок и собрать исходные данные).
Переиспользует: тот же движок сроков из № 1, генератор DOCX. Трудоёмкость: день поверх № 1.

## ЮРИСТУ

**12. Двухпанельный вывод анализа: подсветка в тексте ↔ карточки рисков** `[ВЕЗДЕ]`
Зачем: юрист видит проблемное место прямо в договоре и карточку с объяснением рядом, а не простыню текста.
Подсмотрено: КонсультантПлюс «ИИ-помощник. Договоры» (результат показан одновременно двумя связанными способами, риски разложены на юридические / коммерческие / технические, каждый ведёт в первоисточник нормы).
Переиспользует: парсеры (офсеты), LLM, RAG по нормативке (заполняет поле «источник»), ванильный фронт. Трудоёмкость: неделя.
Бэкенд возвращает не текст, а список `{start, end, level, category, title, explanation, sources[]}`; фронт — `<mark data-id>` и список карточек. У него уже есть RAG по нормативке РФ — значит цитата нормы бесплатна, чего нет ни у кого из офлайн-конкурентов.

**13. Вопрос «на чьей вы стороне» перед стартом** `[ВЕЗДЕ]`
Зачем: «штраф 0,5% в день» — риск для одной стороны и защита для другой; без этого модель выдаёт нейтральную кашу.
Подсмотрено: КонсультантПлюс (один селект «заказчик / исполнитель» меняет весь вывод) + LegalOn (готовые плейбуки различаются по переговорной позиции).
Переиспользует: существующий юр. анализ, один селект в форме и одна строка в промпте. Трудоёмкость: день.
Самое выгодное соотношение «эффект / затраты» во всём каталоге.

**14. Разбор пункт-за-пунктом с восстановлением нумерации** `[ВЕЗДЕ]`
Зачем: модель ссылается на «пункт 4.2.1», а не на «где-то в разделе про ответственность» — и это можно проверить.
Подсмотрено: инженерный разбор на Хабре (номера пунктов физически нет в тексте абзаца, он вычисляется Word'ом — надо парсить `word/numbering.xml`; плюс Schema Guided Reasoning: жёсткая JSON-схема «номер пункта / уверенность 0–1 / краткое объяснение» превращает LLM из болтливого ассистента в структурный классификатор).
Переиспользует: парсеры (python-docx/lxml, новых зависимостей ноль), Ollama с `format:json`. Трудоёмкость: неделя.
Обязательно: валидатор JSON с одним ретраем и отбраковка по confidence — 7B держит схему хуже больших моделей.

**15. Префильтр по таблице типовых рисков** `[ВЕЗДЕ]`
Зачем: сократить число вызовов модели в разы — прямое решение проблемы скорости на CPU без GPU.
Подсмотрено: тот же разбор на Хабре (клауза сопоставляется с таблицей типовых рисков дешёвым нечётким поиском, LLM зовут только на кандидатов).
Переиспользует: BM25 (уже есть), SQLite для таблицы рисков. Трудоёмкость: неделя.

**16. Правки возвращаются в DOCX как настоящие исправления Word** `[ВЕЗДЕ]` ✅ **СДЕЛАНО**
Зачем: не «отчёт, который надо руками переносить в договор», а «скачайте договор с правками и отправьте контрагенту».
Подсмотрено: Spellbook (правки вносятся ОТ ИМЕНИ ПОЛЬЗОВАТЕЛЯ, а не «AI» — юрист сразу пересылает файл, сохраняя профессиональную ответственность) + библиотека docx-revisions (`w:del` сразу за ним `w:ins` — форматирование окружающих run'ов не разрушается).
Переиспользует: парсеры, python-docx (уже есть). Трудоёмкость: неделя.
Чистый Python, установщик не трогается. Обязательно прогнать на реальных договорах с нумерованными списками — там разметка Word самая капризная.

**17. «Что изменил контрагент и чем это грозит»** `[ВЕЗДЕ]`
Зачем: самая частая реальная задача цикла «отправили — вернули с правками», и модель при этом видит не весь договор, а только дельту — то есть работает быстро на CPU.
Подсмотрено: docx-revisions (`accepted_text` / `original_text` даёт готовую дельту без diff-алгоритма) + Яндекс Нейроюрист (объясняет, что содержательно изменилось) + Spellbook Compare (расхождения классифицированы на «важное / заметное», нерелевантные можно отклонить навсегда).
Переиспользует: парсеры, LLM, SQLite (состояние «отклонено»). Трудоёмкость: неделя.

**18. Протокол разногласий одной кнопкой** `[ВЕЗДЕ]`
Зачем: результат проверки выходит не экраном в приложении, а узнаваемым в РФ документом, который физически нужен юристу и бухгалтерии.
Подсмотрено: Ivo (One-Click Issues List — список замечаний в том виде, в каком его реально пересылают контрагенту).
Переиспользует: генератор писем на фирменном бланке — механизм уже готов целиком. Трудоёмкость: день.

**19. Плейбук клиента: правила + библиотека формулировок + fallback** `[ВЕЗДЕ]`
Зачем: «мы оцифровали ваши договорные позиции» — отдельная платная работа при внедрении, и ровно его УТП, положенное в таблицы.
Подсмотрено: LegalOn (три раздельные сущности: плейбук с правилами, clause library с предпочтительной формулировкой и fallback-вариантами по убыванию выгодности, шаблоны).
Переиспользует: SQLite (3 таблицы), RAG, ванильный фронт для редактора правил. Трудоёмкость: месяц.
Ограничение честное: качественный плейбук пишет юрист клиента, значит нужен простой UI-редактор правил, а не JSON-файл.

**20. Импорт внутреннего регламента текстом → правила плейбука сами** `[ВЕЗДЕ]`
Зачем: клиенту не надо заполнять форму из 200 полей — он вставляет кусок своего регламента как есть.
Подсмотрено: Ivo («paste a section from your internal legal standards documentation», модель сама вытаскивает правила).
Переиспользует: существующий пайплайн «вопрос по документу», только на выходе JSON-список правил. Трудоёмкость: неделя.
Экономит дни на каждом внедрении в новой фирме — прямой множитель бутиковой модели.

**21. «В ваших 40 предыдущих договорах этот пункт писали так»** `[ВЕЗДЕ]`
Зачем: архив клиента становится эталоном нормальности — совсем другая ось, чем «соответствие закону», и абсолютно недоступная облакам, куда архив не отдадут.
Подсмотрено: Genie AI (сравнение не с абстрактным «правильно», а с рыночной нормой) + Kira Quick Study (эксперт размечает примеры по ходу обычной работы, модель появляется побочным продуктом).
Переиспользует: ChromaDB + BM25 целиком, LLM для самого поиска не нужен. Трудоёмкость: неделя.
Побочная выгода: чем дольше клиент работает, тем точнее система именно у него — естественное удержание.

**22. Цитата с проваливанием в первоисточник + честное «в базе нет основания»** `[ВЕЗДЕ]`
Зачем: юрист не поверит генерации, но проверит цитату за две секунды; а уверенный тон при пустой выдаче убивает доверие навсегда.
Подсмотрено: kotaemon (ответ открывает встроенный PDF-вьюер, подсвечивает фрагмент и показывает relevance score) + Harvey (цитирование с точностью до предложения) + разобранный публично провал GPT4All LocalDocs (галлюцинированные цитаты при промахе поиска).
Переиспользует: RAG (надо начать сохранять офсеты при индексации), pdf.js — ванильный JS без сборки. Трудоёмкость: неделя.

**23. Светофор с гранулярностью до фразы и до числа** `[ВЕЗДЕ]`
Зачем: пункт о расторжении целиком нормальный, но срок уведомления внутри него — красный.
Подсмотрено: Luminance Traffic Light Analysis (единица подсветки — не пункт, а фрагмент).
Переиспользует: офсеты после парсинга, CSS-класс на `<mark>`. Трудоёмкость: день поверх № 12.
Заставить модель возвращать точную подстроку-цитату и искать её нечётко — 7B склонны перефразировать.

## СЕКРЕТАРЮ И ДЕЛОПРОИЗВОДИТЕЛЮ

**24. Документ собирается опросником** `[ВЕЗДЕ]` `[БЕЗ ИИ]`
Зачем: новый тип документа у нового клиента добавляется файлом шаблона и файлом описания — без правки кода и без пересборки установщика.
Подсмотрено: Doczilla и FreshDoc (вариативность зашита в сам шаблон формулами и условиями) + docassemble (три слоя: YAML-интервью, Python для вычислений, DOCX-шаблон, который юрист рисует в обычном Word; система сама вычисляет, какие вопросы нужно задать, и не задаёт лишних).
Переиспользует: генератор DOCX на фирменном бланке, ванильный фронт. Трудоёмкость: месяц.
Детерминированный шаблонизатор надёжнее модели и работает мгновенно — LLM для генерации договоров не нужен вообще.

**25. Согласование окончаний при подстановке** `[ВЕЗДЕ]` `[БЕЗ ИИ]`
Зачем: «ООО "ПожСервис" заключил» вместо «заключило» бросается в глаза сразу, и российский пользователь за такую мелочь прощает многое.
Подсмотрено: Doczilla (автоматическая замена окончаний по роду, числу и падежу при подстановке наименований и сумм).
Переиспользует: генератор DOCX; pymorphy3 — чистый Python, офлайн, установщик переживёт. Трудоёмкость: день.

**26. Подсветка незаполненных полей** `[ВЕЗДЕ]` `[БЕЗ ИИ]`
Зачем: документ физически нельзя отдать недоделанным.
Подсмотрено: FreshDoc (простая, но сильная деталь UX).
Переиспользует: ванильный фронт. Трудоёмкость: полдня.

**27. Постраничные операции со сканами** `[ВЕЗДЕ]` `[БЕЗ ИИ]`
Зачем: реальность клиента — пачка PDF, где три разных документа в одном файле, страницы вверх ногами и одна потерялась.
Подсмотрено: Papermerge (удалить, повернуть, переставить, вырезать, склеить, ИЗВЛЕЧЬ страницы в другой документ — и любая операция создаёт новую версию, исходник неприкосновенен).
Переиспользует: парсеры; pypdf/pikepdf — чистый Python. Трудоёмкость: неделя.
Принцип «оригинал цел, каждая операция = новая версия» стоит взять для ВСЕХ функций, включая правку договоров.

**28. Двухпанельный файловый менеджер** `[ВЕЗДЕ]` `[БЕЗ ИИ]`
Зачем: для пользователей 40+ это интерфейс Norton/Total Commander — обучение занимает ноль минут, и это выгодно отличает от «ещё одного веб-списка».
Подсмотрено: Papermerge Dual Panel (drag-and-drop между панелями).
Переиспользует: ванильный фронт без сборки. Трудоёмкость: неделя.

**29. Коннектор к папке вместо ручной загрузки** `[ВЕЗДЕ]`
Зачем: документы у клиента лежат в сетевой шаре, а не загружаются кнопкой — система должна приходить к ним, а не наоборот.
Подсмотрено: Onyx/Danswer (ценность не в RAG, а в том, что знания подтягиваются оттуда, где сотрудники их реально держат, плюс отслеживание свежести).
Переиспользует: очередь задач, классификатор документов, парсеры. Трудоёмкость: неделя.

**30. Рабочие области вместо кнопок** `[ВЕЗДЕ]`
Зачем: «отдел кадров», «договоры», «нормативка НЛМК» — это не разные экраны в коде, а конфигурируемые области с разными промптами и разными коллекциями.
Подсмотрено: AnythingLLM (workspace — наборы документов жёстко изолированы, у каждого свои настройки модели и промпта; мультиарендность без мультиарендности). MIT, код можно копировать буквально.
Переиспользует: ChromaDB (коллекции уже есть), SQLite, ванильный фронт. Трудоёмкость: месяц.
Превращает разовую кастомизацию в настройку — прямая механика его УТП.

## ИНЖЕНЕРУ ПО ОХРАНЕ ТРУДА И ПОЖАРНОЙ БЕЗОПАСНОСТИ

**31. Наряд-допуск с автопроверкой допусков бригады** `[ЗАКОН]` `[ОТРАСЛЬ]`
Зачем: система не даёт выпустить наряд, если у члена бригады просрочены обучение, допуск или медосмотр — ответственный перестаёт бегать по отделам за справками.
Подсмотрено: АИС «ВН» в АЛРОСА на 1С:ПБ, ПК «МУНДиР» (сознательно сделан внутрисетевым веб-приложением без установки на рабочие места — ровно его архитектура), Tactise ИНДОРА.
Переиспользует: SQLite (джойн «наряд + бригада + допуски»), генератор DOCX, RAG для описания опасностей и мероприятий по виду работ. Трудоёмкость: месяц.
Самое точное попадание в его текущего клиента: подрядчик НЛМК живёт нарядами. Офлайн здесь не минус, а требование — промплощадка часто без сети. Продавать цифрой: «ноль нарядов с просроченным допуском».

**32. Пакет документов по ОТ и ПБ из одной карточки сотрудника** `[ЗАКОН]` `[ВЕЗДЕ]`
Зачем: один ввод — много документов: программы стажировки, протоколы инструктажей, приказы, графики медосмотров штампуются из справочников.
Подсмотрено: SUOT-ONLINE (принцип «один ввод — много документов» + модульная нарезка по видам безопасности, каждый модуль — отдельный чек тому же клиенту).
Переиспользует: генератор DOCX на бланке (готов на 60%), SQLite-справочники, RAG (обоснование каждого пункта ссылкой на приказ). Трудоёмкость: месяц.
Продаётся тем же людям: в малой фирме специалист по ОТ и по ПБ часто ОДИН человек, часто в самой ПожСервис.

**33. Учёт огнетушителей и первичных средств пожаротушения со сроками перезарядки** `[ЗАКОН]` `[ОТРАСЛЬ]` `[БЕЗ ИИ]`
Зачем: его собственная отрасль, целиком офлайн, механика та же, что у поверки приборов, и внедряется на первом же клиенте.
Подсмотрено: механика ФГИС «Аршин» (юридический факт — запись в реестре, а не бумага на руках), упрощённая до полностью офлайновой картотеки.
Переиспользует: движок сроков из № 1, SQLite, генератор DOCX (журнал учёта). Трудоёмкость: неделя.

**34. Пересборка программ инструктажа при изменении нормативки** `[ЗАКОН]` `[ОТРАСЛЬ]`
Зачем: система живёт триггером «нормативка изменилась → пересобрать программы», а не ждёт, пока кто-то заметит новый приказ.
Подсмотрено: ИС СОТ и 1С:Охрана труда (автоматический пересмотр программ при смене нормативки, СОУТ, оборудования или должностных обязанностей).
Переиспользует: RAG по нормативке, генератор DOCX, очередь задач. Трудоёмкость: месяц.

**35. «Какие ваши регламенты протухли после изменения нормы»** `[ВЕЗДЕ]`
Зачем: связка «пункт внешней нормы ↔ внутренний документ клиента» — половина этого продукта у него уже построена.
Подсмотрено: Техэксперт / Кодекс СУ НТД (единый фонд: внешняя норма связана с внутренним регламентом предприятия, при изменении ГОСТа видно, что устарело).
Переиспользует: ChromaDB с корпусом нормативки, BM25, SQLite для связей. Трудоёмкость: месяц.
Ограничение честное: обновление корпуса норм офлайн — вручную при визите. Для бутикового внедрения это не баг, а повод для абонентки.

**36. Пакет исполнительной документации с проверкой комплектности** `[ЗАКОН]` `[ОТРАСЛЬ]`
Зачем: прораб ведёт реестр работ, материалов и сертификатов, а сотни актов скрытых работ падают пачкой со ссылками на нормативку и паспорта.
Подсмотрено: Адепт: Исполнительная документация, проПТО, Стройформ (нормализованный справочник объекта — умное здесь не редактор актов, а то, что акт собирается подстановкой; комплектность проверяется правилами, а не моделью).
Переиспользует: генератор писем на бланке (это уже 60% движка актов), пакетная проверка → пакетная генерация, RAG на СП/ГОСТ. Трудоёмкость: месяц.
Тот же круг подрядчиков НЛМК, откуда пришёл ПожСервис. Рынок занят закрытыми продуктами — заходить своим УТП и ИИ-сверкой формулировок акта, чего у них нет.

**37. Чек-листы и опросные листы с ветвлением** `[ОТРАСЛЬ]` `[БЕЗ ИИ]`
Зачем: приёмка объекта и обследование — это анкета с условной логикой, а не плоская форма.
Подсмотрено: SurveyJS Form Library (visibleIf, requiredIf, вычисляемые значения, динамические панели, пошаговые мастера — всё атрибутами в JSON, ни строки JS; явно заявлена офлайн-работа). MIT, кладётся в static/, ноль pip-зависимостей.
Переиспользует: ванильный фронт, SQLite. Трудоёмкость: день.

Переиспользует: SQLite (три таблицы связей), ванильный фронт. Трудоёмкость: неделя.

## БОНУС: не функции для продажи, а рычаги, которые делают всё остальное дешевле

Эти пять не показывают клиенту, но без них на пятом внедрении он утонет в форках. По совокупности они стоят примерно две недели и снимают недели на КАЖДОМ клиенте.

**Б1. Экспорт и импорт конфигурации клиента одной командой.** `export-config <клиент>` → JSON-каталог со всеми настройками, шаблонами, справочниками и полями; `import-config` обратно. Подсмотрено: Metabase (продаёт сериализацию как платную фичу — распознали, что операционная зрелость стоит дороже фич) + iDempiere 2Pack (клиентская доработка становится версионируемым артефактом с номером версии и идемпотентной установкой) + Frappe `bench export-fixtures` (настройка мышкой автоматически превращается в артефакт в git). Для SQLite это несколько SELECT в JSON и обратно. **Если делать что-то одно из всего каталога — это.** Трудоёмкость: неделя.

**Б2. Дельта-переопределения интерфейса вместо правки кода.** Таблица `ui_override(client, entity, field, prop, value)`, читаемая при сборке формы: подпись, обязательность, скрытость, порядок меняются данными. Подсмотрено: Frappe Property Setter — самая копируемая идея во всём исследовании. Плюс из Битрикса: подписей держать НЕСКОЛЬКО — для формы, для колонки списка, для фильтра («Гос. регистрационный знак ТС» и «Госномер» — норма, а не исключение). Трудоёмкость: неделя.

**Б3. Точки расширения в HTML вместо форка шаблона.** `<div data-outlet="letter.form.after">`, ядро при загрузке подхватывает `extensions/<клиент>/ui/*.js` и монтирует туда. Подсмотрено: Discourse plugin outlets (сотни именованных выходов + служебный режим, подсвечивающий их имена прямо на странице — кастомизатору не надо читать исходники ядра) + Odoo XPath-патчинг видов. Идеально ложится на ванильный фронт без сборки — это, по сути, и есть подход без сборки. Дисциплина: только добавлять до/после, никогда не заменять целиком. Трудоёмкость: неделя.

**Б4. Дополнительные поля клиента — sidecar-таблицей, не EAV.** Определения в одной таблице, значения — в `<entity>_extra` реальными колонками через ALTER TABLE ADD COLUMN (в SQLite это O(1), backfill не делается). Подсмотрено: Dolibarr Extrafields и Битрикс `b_uts_*` (одиночные значения широкой таблицей, множественные — отдельной узкой; не пытаться сделать одну схему на оба случая) + отрицательный урок Corteza (чистый EAV убил у них производительность, фильтрацию и отчётность — на SQLite будет хуже). Плюс приём Baserow: технические имена колонок `field_{id}`, человеческая подпись живёт только в метаданных — для русских подписей это фактически обязательно. Трудоёмкость: день.

**Б5. Промпты в SQLite с версиями, а не в Python.** Промпт под конкретного клиента правится без релиза и откатывается. Подсмотрено: Dify (промпт как версионируемый артефакт с привязанным датасетом и тестовым прогоном) — но код Dify брать НЕЛЬЗЯ: их лицензия запрещает удалять логотип и требует коммерческую лицензию на мультиарендность, то есть прямо конфликтует с белым лейблом и моделью «инсталляция на клиента». Только идея. Трудоёмкость: день.

## Три предупреждения, чтобы не потерять время

**Лицензии.** ToolJet, Documenso, Khoj, Twenty, SuiteCRM, ToolJet — AGPL: код не подмешивать к закрытой поставке. Open WebUI с v0.6.6 запрещает убирать брендинг при более чем 50 пользователях за 30 дней (сейчас он в исключении на 30 пользователях, но клиент вырастет). Dify — запрет удалять логотип. Paperless-ngx под GPL — копировать модель данных и UX можно, код нельзя. Безопасны для копирования: Datasette, Grist, Baserow-ядро, Docling, sqladmin, Tabulator, json-editor, SurveyJS-рендерер, AnythingLLM.

**Не браться.** Полный OCR первички на CPU (разочарует на кривых сканах), визуальный конструктор процессов (ловушка для одиночки), рантайм-генерация API из метаданных (отладка становится невозможной), чистый EAV, Python-Redlines в первой итерации (предсобранный .NET-бинарь плюс корпоративный антивирус на Windows-сервере — реальный риск, держать вторым эшелоном и проверить на целевой машине до обещаний). Docling — только опциональным «точным режимом» для сложных PDF с фолбэком: тянет torch.

**Две готовые библиотеки вместо своих 300 строк.** `@json-editor/json-editor` (MIT, 536 КБ, ноль зависимостей, один тег `<script>`) делает форму из схемы, `Tabulator` (MIT) делает список с сортировкой, фильтрами и правкой на месте. Вместе — полный CRUD-экран из двух JSON-описаний, без Node, без сборки, без единого нового pip-пакета, полностью офлайн. Один `renderScreen(cfg)`, один generic-роутер на сыром SQLite, один словарь на справочник в духе Django Admin (`list_display`, `search_fields`, `fieldsets`, `actions`) — и новый справочник клиента становится 15 строками конфига вместо недели. Это и есть рычаг «неделя → час», ради которого стоит потратить ближайший день.

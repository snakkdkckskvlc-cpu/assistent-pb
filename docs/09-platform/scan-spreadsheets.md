# ГЛАВНЫЙ ВЫВОД. Все AI-таблицы 2025-26 (Copilot, Gemini, Rows, Numerous, Bricks, МойОфис 26.2) делают одно и то же: болтают с таблицей. На 7B офлайн это не воспроизвести и не нужно — там, где ИИ генерит значения ячеек, он врёт, а бухгалтер обязан проверить каждую строку, то есть экономии ноль. Ценность лежит в другом месте, и её видно у Grist и у российских программ сверки.

ДВА АРХИТЕКТУРНЫХ ПРАВИЛА, которые делают всё это реальным на его стеке:
(1) LLM НИКОГДА не касается чисел. Модель выдаёт ПРАВИЛО (маппинг, регэксп, спецификацию группировки, соответствие колонок) — детерминированный движок применяет правило ко всем строкам и показывает превью. Проверить одно правило дёшево, проверить 500 сгенерированных ячеек — дороже, чем сделать руками. Это буквально модель Grist: trigger-формулы + превью импорта.
(2) ПАМЯТЬ ВМЕСТО МОДЕЛИ. Каждое исправление пользователя пишется в SQLite как (нормализованный текст → результат). Следующий раз — мгновенный lookup без модели. Через месяц LLM зовётся на <5% строк. Именно так работает разнесение выписки в Контур/банках — это таблица соответствий, а не нейросеть.

ЧТО ТАКОЕ СВЕРКА (главный ответ на вопрос 3). Российская SverkaPro раскрывает алгоритм: КАСКАД из 4 ключей сопоставления по убыванию строгости — Дата+Номер+Сумма → Номер+Сумма → Дата+Сумма → просто Сумма. Каждая строка красится в цвет того метода, которым сопоставилась: строгое совпадение — зелёное, «только по сумме» — жёлтое (смотри глазами), не сопоставлено — красное. Отдельно — нормализация номеров документов: «Приход (17168)» и «Счёт-фактура № УТ000017168» это один документ (снять префиксы, слеши, тире, ведущие нули, оставить цифровое ядро). Плюс обработка сторно. Сервис CORRECT добавляет финальный шаг: из расхождений автоматически формируется протокол/акт разногласий на отправку контрагенту. Ни грамма ИИ во всём этом нет — чистая детерминированная логика, работает мгновенно и не врёт. Это самая ценная находка отчёта.

GRIST (вопрос 4) — там украдено три вещи. Первая: формула принадлежит СТОЛБЦУ, а не ячейке. Нет копирования вниз, нет «формула поехала», нельзя случайно затереть одну ячейку из тысячи — 90% ошибок Excel исчезают как класс. Вторая: trigger-формула — считается только при создании или изменении записи, видит переменные value (что ввёл пользователь) и user (кто ввёл), а дальше значение остаётся обычным редактируемым данным. Это идеальный механизм для «подставь по справочнику при вводе, но дай перебить руками» и для автозаполнения полей типа «кто и когда изменил». Третья и самая сильная: ИМПОРТ С ОБНОВЛЕНИЕМ. Выбираешь merge fields (ключевые колонки), Grist считает совпадающие записи одной и показывает превью: зелёное — новая запись, красное зачёркнутое → зелёное — изменившееся поле, без подсветки — без изменений. Пустые значения в импорте не затирают существующие. Явно описаны правила разрешения конфликтов (при дублях в импорте берётся последняя строка, при дублях в базе обновляется первая запись). Это готовый UX сверки, отданный бесплатно. AI-ассистент Grist пишет формулы и подключается к любому OpenAI-совместимому эндпойнту (люди подключали Ollama через ASSISTANT_CHAT_COMPLETION_ENDPOINT) — то есть даже Grist не доверяет ИИ значения, только код формулы.

ЧТО ТРЕБУЕТ LLM, А ЧТО НЕТ (вопрос 2 — самый важный практически). БЕЗ МОДЕЛИ, мгновенно: сверка, поиск дублей, контрольные суммы ИНН/КПП/ОГРН/СНИЛС/БИК, распознавание типов колонок, парсинг дат/сумм, сводные (это group by в SQLite), транспонирование, unpivot, кросс-проверки (итог = сумма строк, НДС бьётся), заполнение по образцу. Последнее особенно: Excel FlashFill — это НЕ нейросеть, а синтез программ над узким DSL (Concatenate / Substring по регэкспу или позиции / ConstantString) методом version space algebra, из 1-2 примеров. Урезанная версия на 6-8 операций пишется на чистом Python за неделю. РЕАЛЬНО ТРЕБУЕТ LLM только три вещи: семантическое разнесение свободного текста по категориям (и то как последний фолбэк после памяти и fuzzy), перевод запроса словами в спецификацию группировки, и прозаическое объяснение сложной формулы.

ПРО СТЕК (вопрос 5). Проверил его requirements-runtime.txt: openpyxl и pandas НЕ стоят, numpy стоит. Рекомендация — добавить ТОЛЬКО openpyxl: чистый Python, без компиляции, без транзитивных зависимостей, установщику ничего не грозит. pandas НЕ НАДО: 60 МБ бинарного колеса ради того, что на 30 пользователях и тысячах строк делается через csv + sqlite3 + openpyxl, причём вся группировка и джойны — обычным SQL по уже имеющейся SQLite. Fuzzy-сравнение — difflib.SequenceMatcher из стандартной библиотеки, ноль новых зависимостей (rapidfuzz быстрее, но это C++-колесо, брать только если difflib реально не потянет). ГРАБЛИ openpyxl, которые надо знать заранее: формулы НИКОГДА не вычисляются — load_workbook(data_only=True) отдаёт значение, закешированное Excel при последней записи, и если файл сгенерирован программно, там будет None; объединённые ячейки хранят значение только в левой верхней, остальные None (шапки российских ведомостей — сплошь объединённые, это первое, обо что споткнётся парсер); для больших файлов есть read_only (ленивая загрузка) и write_only (память до 10 МБ).

ЧЕГО НЕТ НИ У КОГО И ЧТО СТОИТ УКРАСТЬ. Ни Copilot, ни Gemini, ни МойОфис не делают АУДИТ ЧУЖОЙ КНИГИ — формула-«белая ворона», выбивающаяся из паттерна столбца; числа, записанные текстом; SUM, не покрывающий дописанные снизу строки; скрытые строки внутри диапазона. Это на 100% детерминированно, это ровно та ошибка, которая стоит бухгалтеру дня разбирательств, и это дифференциатор, которого нет даже у Microsoft.

## Загрузить обновление и увидеть, что изменилось  (неделя, офлайн: Да, модель не нужна. Механизм чисто детерминированный, отсюд)

**Боль:** Прислали новый прайс поставщика, новый список сотрудников на пропуска, обновлённый реестр объектов. Надо влить в свою таблицу, не наплодив дублей и понимая, что именно поменялось. Сейчас это либо ручное перебивание, либо «удалю старое, вставлю новое» с потерей своих пометок.

**Как:** Пользователь указывает ключевые колонки (merge fields) — по ним строки считаются одной и той же записью. Дальше превью до применения: зелёным — новые записи, красным зачёркнутым со стрелкой на зелёное — изменившиеся поля, без подсветки — без изменений. Пустые значения во входном файле НЕ затирают то, что уже есть. Явные правила конфликтов: если в импорте дубли по ключу — берётся последняя строка, если в базе дубли — обновляется первая. Применяется только после нажатия «применить», с записью отката в SQLite.

**Подсмотрено:** Grist, функция «Update existing records» при импорте. Умное — три вещи: (1) само понятие merge fields, выбираемых пользователем, а не зашитых; (2) обязательное превью диффом до записи, а не после; (3) правило «пустое не затирает» — оно неочевидно, но именно оно спасает, когда во входном файле заполнена половина колонок.

**Переиспользует:** SQLite-слой и CRUD уже написаны для адресатов — тот же паттерн. Очередь задач. openpyxl.

## Поиск дублей и склейка написаний  (неделя, офлайн: Да, без модели. LLM тут соблазнительна, но не нужна: нормали)

**Боль:** В реестре один и тот же контрагент записан четырьмя способами: «ООО ПожСервис», «ООО "Пожсервис"», «Пож-Сервис ООО», «ООО  ПОЖСЕРВИС» с двойным пробелом. Сводная по контрагентам разваливается на четыре строки, отчёт неверный. То же с номенклатурой: «Огнетушитель ОП-5 (з)» и «ОП-5 закачной».

**Как:** Три слоя по возрастанию мягкости. Первый: нормализация — регистр, лишние пробелы, кавычки всех видов, организационно-правовая форма выносится в отдельное поле, латиница в кириллических словах чинится. После этого половина дублей схлопывается точным совпадением. Второй: блокинг (группируем кандидатов по первым буквам или по ИНН, чтобы не сравнивать всё со всем) плюс нечёткое сравнение через difflib.SequenceMatcher из стандартной библиотеки. Третий: показать группы-кандидаты пользователю, он выбирает эталон, соответствие пишется в SQLite и в следующий раз применяется мгновенно.

**Подсмотрено:** Rows AI («cleaning messy inputs»), Numerous.ai. Из практики record linkage взят обязательный блокинг — без него нечёткое сравнение квадратично и умирает на первых тысячах строк; rapidfuzz, кстати, блокинг не делает, его надо писать самому. Умное решение — не автоматическая склейка, а группы-кандидаты на подтверждение: цена ошибочной склейки в бухгалтерии слишком высока.

**Переиспользует:** SQLite для словаря эталонов, очередь задач. difflib — стандартная библиотека, ноль новых зависимостей.

**Как:** Три уровня. Первый — память: SQLite-таблица (нормализованное назначение или ИНН плательщика → статья). Если совпало, ответ мгновенный, модель не запускается. ## Заполнение по образцу  (неделя, офлайн: Да, модель не нужна, срабатывает за миллисекунды. Урезанный )

**Боль:** В колонке 400 строк вида «Иванов Иван Иванович», нужна колонка «Иванов И.И.». Или из «г. Липецк, ул. Ленина, д. 5» вытащить улицу. Или из «Договор №12/2025-ПБ от 01.03.2025» — номер отдельно, дату отдельно. Это полдня механического перебивания.

**Как:** Пользователь заполняет 2-3 ячейки руками. Система синтезирует программу над узким DSL: взять кусок до/после разделителя, срез по позиции, группа регэкспа, конкатенация, константа, смена регистра, переформатирование даты. Ключевое, что стоит украсть у FlashFill: это НЕ нейросеть, а синтез программ методом version space algebra над намеренно УЗКИМ DSL — авторы прямо пишут, что общий язык вроде Python сделал бы поиск неуправляемым. Узость DSL — не ограничение, а условие работоспособности.

**Переиспользует:** Ничего не требует, кроме openpyxl. Хорошо ложится в существующий UI загрузки файла.

## Аудит книги Excel  (неделя, офлайн: Да. Важные грабли: openpyxl НИКОГДА не вычисляет формулы. С )

**Боль:** Достался чужой файл — от предыдущего сотрудника, от заказчика, от подрядчика. Внутри может быть что угодно, и подписывать отчёт по нему страшно. Классика: в столбце из 300 формул одна затёрта константой, и итог тихо неверный уже год.

**Как:** Детерминированный набор проверок: формула-«белая ворона» (одна ячейка выбивается из паттерна столбца — самая ценная проверка); числа, записанные текстом; SUM, чей диапазон не покрывает дописанные снизу строки; скрытые строки внутри суммируемого диапазона; ошибки #REF!, #ДЕЛ/0!, #ЗНАЧ!; итог не равен сумме строк; НДС не бьётся с базой; объединённые ячейки, ломающие сортировку и фильтр. Отчёт — список адресов ячеек с объяснением. Здесь важна вторая роль LLM: она НЕ ищет ошибки, а лишь пересказывает найденное человеческим языком.

**Подсмотрено:** Этого нет ни у Copilot, ни у Gemini, ни у МойОфис — они умеют объяснить формулу, которую вы им показали, но не аудировать чужую книгу целиком. Отдельные проверки есть в аудиторских надстройках Excel. Это редкий случай, где можно обогнать Microsoft, потому что задача детерминированная и им просто неинтересная.

**Переиспользует:** Очередь задач, генератор DOCX для отчёта. openpyxl обязателен.

## Сводная и группировка по запросу словами  (неделя, офлайн: Да, при условии что модель порождает только короткий JSON-пл)

**Боль:** «Сколько мы потратили на каждый объект по кварталам» — и человек, который не умеет в сводные таблицы, идёт просить того, кто умеет. Или считает калькулятором.

**Как:** Ключевой приём: LLM выдаёт не ответ и не числа, а СПЕЦИФИКАЦИЮ в JSON — что группировать, что суммировать, какие фильтры, как сортировать. Спецификация валидируется против реальных имён колонок (галлюцинированная колонка отбрасывается сразу), превращается в обычный SQL и исполняется на SQLite, куда таблица залита как временная. Пользователю показывается и результат, и человекочитаемое описание («сгруппировано по объекту и кварталу, просуммирована колонка Сумма»), чтобы он видел, что именно посчитано.

**Подсмотрено:** МойОфис «Документы Настольные» 26.2 (июнь 2026) — ИИ-помощник в редакторе «МояТаблица» строит сводные по запросу на естественном языке; Excel Copilot; Bricks. Умное у Copilot — он показывает не только результат, но и разбор шагов, своё «мышление». Для 7B это не украшение, а обязательное условие доверия.

**Переиспользует:** SQLite уже в стеке — вся группировка это обычный SQL, pandas не нужен. Ollama-клиент, очередь задач.

## Развернуть журнал в плоский список  (день, офлайн: Да, без модели, мгновенно.)

**Боль:** Ведомость ТО или табель, где месяцы или объекты идут по столбцам вправо. По такой таблице невозможно ни отфильтровать, ни сгруппировать, ни свести — а именно в таком виде они и ведутся годами.

**Как:** Unpivot: указанные колонки-заголовки сворачиваются в две колонки «признак» и «значение», остальные размножаются. Плюс транспонирование и обратная операция (плоский список обратно в широкую матрицу для печатной формы). Отдельно — распознавание многоуровневой шапки из объединённых ячеек: их надо развернуть в нормальные заголовки ДО всего остального, иначе любой парсер российской ведомости захлебнётся.

**Подсмотрено:** Power Query в Excel (операция Unpivot), Grist. Общий принцип из Grist и Baserow: держать данные плоскими, а «широкий» вид получать как представление. Технически важное: openpyxl при объединении ячеек хранит значение только в левой верхней, а остальные отдаёт как None — заполнение вниз и вправо по merged_cells надо писать руками, это первое, обо что спотыкается любой парсер российских форм.

**Переиспользует:** Только openpyxl. Функция маленькая, но является предусловием для сводных и группировок — без неё они не заработают на реальных файлах конторы.

## Собрать реестр из пачки документов  (неделя, офлайн: Да, но это самая тяжёлая по времени функция: OCR плюс LLM на)

**Боль:** Сорок счетов и актов в PDF свалены в папку, из них надо руками набить реестр: номер, дата, контрагент, сумма, НДС. Полдня механической работы, в конце которой глаз замылен и три суммы перебиты неверно.

**Как:** Существующие парсеры PDF/OCR и классификатор типа документа уже стоят в проекте — добавляется только слой извлечения полей и сборки в таблицу. Сначала регэкспы по типовым шаблонам («Счёт № ... от ...», «Итого с НДС», «в том числе НДС 20%»), LLM только там, где регэксп не сработал. Каждая строка несёт ссылку на исходный файл и страницу, а поля с низкой уверенностью подсвечиваются — клик открывает документ на нужном месте. Обязательная арифметическая сверка: база плюс НДС равно итогу; не сошлось — строка в красное.

**Подсмотрено:** Rows AI («extracting tables and text from PDFs, screenshots and scans»), сервис CORRECT (OCR акта с извлечением реквизитов: организация, контрагент, период, договор). Умное у CORRECT — распознанное сразу используется как ключ для автоматического поиска парного документа в своей учётной системе, а не просто выводится на экран.

**Переиспользует:** Максимальное переиспользование: парсеры DOCX/PDF/OCR, классификатор типа документа, очередь задач, Ollama-клиент. Из нового — только сборка в XLSX через openpyxl.

## Контроль сроков по реестру  (неделя, офлайн: Да, модель не нужна вовсе. Это самая дешёвая в разработке фу)

**Боль:** Удостоверения ПТМ, аттестации, сроки ТО по объектам, окончание договоров, поверка оборудования — всё лежит в таблицах с колонкой даты. Никто эти таблицы не листает, пока НЛМК не завернёт человека на проходной с просроченным удостоверением.

**Как:** Пользователь один раз показывает: вот колонка с датой окончания, вот колонка с именем, вот за сколько дней предупреждать. Дальше при каждом запуске приложения — детерминированная выборка «истекает через N дней» и «уже просрочено», сводка на главном экране и, по кнопке, письмо ответственному через существующий генератор писем на бланке. Правило хранится в SQLite и переживает перезагрузку таблицы.

**Подсмотрено:** Механически это trigger-формулы Grist — вычисление, привязанное к событию, а не к открытию файла, с доступом к переменным value и user. Умное в самой идее Grist: формула принадлежит СТОЛБЦУ, а не ячейке, поэтому её нельзя случайно затереть в одной строке из тысячи — этим одним решением снимается основной класс ошибок Excel, и этот принцип стоит заложить во все табличные функции проекта.

**Переиспользует:** Генератор писем на бланке, SQLite-слой, планировщик из очереди задач. Прямая синергия с уже сделанным учётом транспорта — путевые листы и сроки ТО автомобилей ложатся сюда же.

## Заполнить чужой шаблон по нашим данным  (неделя, офлайн: Да, без модели. Осторожно с write_only-режимом openpyxl — он)

**Боль:** НЛМК присылает свою форму XLSX — реестр на пропуска, список СИЗ, сводку по инструктажам — со своим порядком колонок и своими заголовками. Данные все есть в своей таблице, но перебиваются в чужую форму руками каждый раз.

**Как:** Один раз настраивается соответствие: колонка нашего реестра → колонка их формы. Сопоставление предлагается автоматически по совпадению и близости заголовков (то же нечёткое сравнение, что и в поиске дублей), пользователь правит, соответствие сохраняется в SQLite под именем формы. Дальше это одна кнопка. Записывается строго в копию присланного файла через openpyxl, чтобы сохранились их форматирование, печатная область и подписи. Перед выгрузкой прогоняется проверка реквизитов — чтобы форма не вернулась из НЛМК с ошибкой.

**Подсмотрено:** Grist при импорте: автоматическое сопоставление колонок с возможностью ручного переопределения и пунктом «Skip» для лишних, плюс возможность применить формулу к импортируемой колонке. Умное — соответствие не угадывается заново каждый раз, а именуется и сохраняется как многоразовая настройка.

**Переиспользует:** SQLite для хранения профилей форм, нечёткое сравнение из функции поиска дублей, валидатор реквизитов. openpyxl умеет открыть чужой файл и дописать в него, сохранив оформление.

## 0. Рамка: три слоя кастомизации и жёсткие инварианты

Всё исследование сходится в одну точку: кастомизация должна лежать в трёх слоях, и порядок между ними иерархический — **сначала строка в БД, потом файл в клиентском пакете, и только в крайнем случае код**.

| слой | где живёт | кто может менять | переживает обновление ядра |
|---|---|---|---|
| 1. Метаданные (поля, формы, справочники, роли, сроки, отчёты) | строки в SQLite клиента | он на встрече, за минуты | автоматически (git ядра их не видит) |
| 2. Клиентский пакет (шаблоны DOCX, JSON-конфиги, статика, hooks.py) | каталог **вне** рабочего дерева git | он, коммитом в отдельный репозиторий клиента | по манифесту совместимости |
| 3. Ядро | рабочее дерево git | только он, и это фича продукта, а не клиента | это и есть обновление |

Инварианты, которые надо записать в `docs/RULES.md` и не нарушать (урок расширений 1С: без регламента слой кастомизации за год превращается во второй конфигуратор):

1. **В ядре нет ни одного `if client == 'pozhservice'`.** Ядро не знает имён клиентов.
2. **Ничего клиентского внутри рабочего дерева git.** Ни БД, ни загрузок, ни `ext/`, ни логов, ни сгенерированных документов.
3. **Поля не переименовываются и не меняют тип. Никогда.** Техническое имя колонки — `f_<id>`, подпись — строка в метаданных.
4. **Удаление поля — флаг `is_deleted`, а не DDL.**
5. **Деньги — целые копейки в INTEGER.** REAL для сумм — источник багов, которые всплывут через год в акте сверки.
6. **Одна инсталляция = одна компания = один файл БД.** Никаких `client_id` в строках. Мультиарендность внутри одной БД — налог, который ему платить не нужно.
7. **Раз в квартал считать «налог на кастом»**: сколько строк клиентского Python не проходит через хуки. Цель — ноль. Odoo намерил, что именно этот объём определяет стоимость каждого будущего обновления (272 часа на инстанс с 24 пользователями и «минимальной доработкой»).

## 1. Схема таблиц для SQLite

### 1.1 Выбор хранения: почему не EAV, не «только JSON» и не таблица-на-клиента

**EAV — нет.** Отрицательный урок Corteza разобран публично: они начали с `compose_record_value(record_id, name, value)` и уперлись в фильтрацию, сортировку и отчёты, после чего добавили маппинг на реальные таблицы. На SQLite это будет хуже, чем на PostgreSQL: каждое поле в `WHERE` — отдельный self-join, планировщик SQLite сдаётся на 4–5 join'ах быстрее. А его домен — это реестры, журналы и сроки, то есть сплошные `WHERE` и `ORDER BY`.

**Только JSON — нет,** но как режим для части полей — да. Фильтрация требует `json_extract`, индекс требует virtual generated column, отчёты руками писать больно. Правило-разделитель, которое надо зафиксировать письменно: **если поле хоть раз появится в WHERE, ORDER BY, в отчёте или в движке сроков — это колонка. Иначе — json.** На практике 80% полей окажутся колонками.

**Таблица (или БД) на клиента — уже есть и это правильно.** Отдельный файл SQLite на внедрение — это «схема на арендатора» из Twenty, только бесплатно. Именно поэтому не нужен `client_id`.

**Итог: гибрид Dolibarr + Baserow + Directus.** Определения — в метатаблицах. Значения — реальными типизированными колонками с техническими именами `f_<id>`. Для ядровых сущностей — в sidecar-таблице `<table>_x`, чтобы его собственные миграции ядра физически не могли конфликтовать со схемой клиента. Для клиентских справочников — своя настоящая таблица `c_<key>`. Редкие атрибуты — в `x_json`.

### 1.2 Метатаблицы

```sql
-- Сущность: и ядровая (addressees, vehicles), и клиентская (огнетушители, инструктажи)
CREATE TABLE meta_entity (
  key         TEXT PRIMARY KEY,            -- 'addressees', 'extinguishers'
  table_name  TEXT NOT NULL,               -- 'addressees' | 'c_extinguishers'
  kind        TEXT NOT NULL,               -- 'core' | 'client'
  title_one   TEXT NOT NULL,               -- 'Огнетушитель'
  title_many  TEXT NOT NULL,               -- 'Огнетушители'
  title_acc   TEXT,                        -- 'огнетушитель' (для "Удалить ...?")
  menu_group  TEXT,                        -- раздел меню
  menu_ord    INTEGER NOT NULL DEFAULT 100,
  owner_col   TEXT,                        -- колонка "чья запись" (для прав read_own)
  page_tpl    TEXT,                        -- если задано — своя HTML-страница вместо generic
  is_enabled  INTEGER NOT NULL DEFAULT 1,
  origin      TEXT NOT NULL DEFAULT 'core' -- 'core' | 'pack' | 'local'
);

-- ФИЗИЧЕСКАЯ половина поля: то, что влияет на схему БД. Правка = потенциальный DDL.
CREATE TABLE meta_field (
  id          INTEGER PRIMARY KEY,
  entity_key  TEXT NOT NULL REFERENCES meta_entity(key),
  col         TEXT NOT NULL,               -- 'f_17' для клиентских, 'name' для ядровых
  type        TEXT NOT NULL,               -- text|longtext|int|money|num|date|datetime|bool|enum|ref|file
  storage     TEXT NOT NULL DEFAULT 'column', -- 'column' | 'json'
  ref_entity  TEXT,                        -- для type='ref'
  enum_key    TEXT,                        -- для type='enum'
  required    INTEGER NOT NULL DEFAULT 0,
  default_val TEXT,
  is_deleted  INTEGER NOT NULL DEFAULT 0,  -- логическое удаление, DDL не делаем
  origin      TEXT NOT NULL DEFAULT 'core',
  UNIQUE(entity_key, col)
);

-- КОСМЕТИЧЕСКАЯ половина: подписи, виджеты, условия. Правка НИКОГДА не трогает схему.
CREATE TABLE meta_field_ui (
  entity_key   TEXT NOT NULL,
  col          TEXT NOT NULL,
  form_label   TEXT NOT NULL,   -- 'Государственный регистрационный знак ТС'
  list_label   TEXT,            -- 'Госномер'
  filter_label TEXT,
  hint         TEXT,
  widget       TEXT,            -- input|textarea|select|date|checkbox|ref|money|file
  section      TEXT,            -- группа/вкладка на форме
  width        TEXT,            -- '1','1/2','1/3'
  ord          INTEGER NOT NULL DEFAULT 100,
  in_list      INTEGER NOT NULL DEFAULT 0,
  in_filter    INTEGER NOT NULL DEFAULT 0,
  in_search    INTEGER NOT NULL DEFAULT 0,
  readonly     INTEGER NOT NULL DEFAULT 0,
  visible_if   TEXT,            -- JSON-условие, см. п.2.3
  required_if  TEXT,
  options_json TEXT,            -- маска, min/max, точность, формат
  PRIMARY KEY(entity_key, col)
);

CREATE TABLE meta_enum_item (
  enum_key TEXT NOT NULL, code TEXT NOT NULL, label TEXT NOT NULL,
  ord INTEGER NOT NULL DEFAULT 100, color TEXT,
  is_active INTEGER NOT NULL DEFAULT 1,
  PRIMARY KEY(enum_key, code)
);
```

Разделение `meta_field` / `meta_field_ui` — это ровно `schema` vs `meta` из Directus, и оно даёт три вещи: (а) видно, какая правка требует ALTER TABLE, а какая нет; (б) на объекте у клиента безопасно правится только `_ui`; (в) при экспорте пакета `_ui` можно перезаписывать целиком, а `meta_field` — только доливать.

Три подписи вместо одной — приём Битрикса, и на его домене это не роскошь: в форме «Государственный регистрационный знак ТС», в таблице «Госномер», в фильтре «Госномер или марка».

### 1.3 Таблицы данных

Клиентский справочник:
```sql
CREATE TABLE c_extinguishers (
  id         INTEGER PRIMARY KEY,
  f_1 TEXT, f_2 TEXT, f_3 TEXT, f_4 INTEGER,   -- заводит генератор из meta_field
  x_json     TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT,
  created_by INTEGER,
  is_deleted INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX ix_c_extinguishers_live ON c_extinguishers(is_deleted);
```

Sidecar к ядровой сущности (Dolibarr `llx_*_extrafields` / SuiteCRM `*_cstm`):
```sql
CREATE TABLE addressees_x (
  id     INTEGER PRIMARY KEY REFERENCES addressees(id) ON DELETE CASCADE,
  f_9    TEXT,
  f_10   INTEGER,
  x_json TEXT NOT NULL DEFAULT '{}'
);
CREATE TRIGGER trg_addressees_x AFTER INSERT ON addressees
BEGIN INSERT OR IGNORE INTO addressees_x(id) VALUES (NEW.id); END;
```
Чтение — обычный `LEFT JOIN`. Триггер нужен, чтобы никто никогда не забыл создать sidecar-строку; создаётся тем же генератором.

### 1.4 Что делать с существующей `addressees` — не мигрировать

Это самая важная практическая деталь. **Не переносить существующие таблицы в метадвижок.** Вместо этого — ход Directus: источником истины остаётся реальная схема, метаданные лишь надстройка.

```
python -m tools.introspect addressees
```
читает `PRAGMA table_info('addressees')`, создаёт строку в `meta_entity` (kind='core') и по строке в `meta_field`/`meta_field_ui` на каждую существующую колонку с `origin='core'` и разумными дефолтами (тип по affinity, подпись = имя колонки, `in_list=1` для первых трёх). Дальше он правит подписи руками за 10 минут.

Результат: `addressees` физически не изменилась, весь текущий код с ней работает как работал, но generic-экран её уже умеет рисовать, а клиентские допполя ложатся в `addressees_x`. Регистрация всех его существующих 10–15 таблиц занимает вечер, а не спринт. Это же скрипт-интроспектор — готовый инструмент внедрения: приехал к новому клиенту, натравил на его выгрузку, получил каркас.

### 1.5 Генератор схемы (идея Twenty, ~120 строк, ноль зависимостей)

```
desired = meta_field WHERE storage='column' AND is_deleted=0
actual  = PRAGMA table_info(<table_name>)
diff    → только ADD COLUMN
```

Проверенные ограничения SQLite (проверял на 3.51; на его сервере надо один раз проверить `sqlite3.sqlite_version` — нужен минимум 3.35):

| операция | результат |
|---|---|
| `ADD COLUMN` в непустую таблицу | O(1), правится только запись схемы, backfill не делается |
| `ADD COLUMN ... NOT NULL` без DEFAULT в непустую | **ошибка** — `Cannot add a NOT NULL column with default value NULL` |
| `ADD COLUMN ... DEFAULT (datetime('now'))` в непустую | **ошибка** — `Cannot add a column with non-constant default` |
| `ADD COLUMN ... GENERATED ... STORED` | **ошибка** — `cannot add a STORED column` |
| `ADD COLUMN ... GENERATED ... VIRTUAL` | работает, и по такой колонке **можно строить индекс** |
| `CREATE INDEX ... ON t(json_extract(x_json,'$.k'))` | работает (индекс по выражению) |
| `DROP COLUMN` / `RENAME COLUMN` | 3.35+ / 3.25+, но мы их **не используем никогда** |

Отсюда жёсткие правила генератора: колонки всегда добавляются **nullable без DEFAULT**, обязательность (`required`) проверяется в приложении, а не в схеме; для JSON-поля, по которому вдруг понадобилось фильтровать, добавляется virtual generated column + индекс — это единственный законный способ «доиндексировать задним числом».

Смена типа поля запрещена (матрицу конверсий Baserow копировать не надо): в UI при попытке — «создайте новое поле», старое помечается `is_deleted=1`. Значения при необходимости переносит одноразовый SQL.

Маппинг типов: `text/longtext/date/datetime/enum → TEXT`, `int/bool/ref → INTEGER`, `money → INTEGER (копейки)`, `num → REAL`, `file → TEXT` (относительный путь в data-root).

### 1.6 Движок сроков — сюда же, потому что он тоже метаданные

Единственный блок, которого нет ни в одном виде и который окупается в каждой вертикали (ОТ, пожарка, транспорт, экология, метрология). Ни LLM, ни новых зависимостей.

```sql
CREATE TABLE meta_deadline_rule (
  id INTEGER PRIMARY KEY,
  entity_key TEXT NOT NULL,
  date_col   TEXT NOT NULL,                    -- какое поле — дата истечения
  offsets    TEXT NOT NULL DEFAULT '30,7,0',   -- за сколько дней предупреждать
  title_tpl  TEXT NOT NULL,                    -- 'Истекает перезарядка: {f_1} ({f_3})'
  filter_sql TEXT,                             -- 'is_deleted=0 AND f_9=1'
  roles      TEXT,                             -- кому показывать
  is_enabled INTEGER NOT NULL DEFAULT 1
);
CREATE TABLE deadline_hit (
  id INTEGER PRIMARY KEY,
  rule_id INTEGER NOT NULL, entity_key TEXT NOT NULL, row_id INTEGER NOT NULL,
  due_date TEXT NOT NULL, offset_days INTEGER NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  ack_by INTEGER, ack_at TEXT,
  UNIQUE(rule_id, row_id, offset_days)
);
```
Скан — фоновая корутина в `lifespan` FastAPI, просыпается раз в час, `UNIQUE` гарантирует, что одно и то же не всплывёт дважды. Никакого Celery и никакого APScheduler (лишняя зависимость в хрупкий установщик). Новый клиент = 5–7 строк в `meta_deadline_rule`.

## 2. Рендер формы без сборки фронтенда

### 2.1 Вердикт: писать своё, ~350 строк, библиотеки не тащить

Против Amis: 4,4 МБ статики, собственный визуальный язык (либо он принимает вид Amis целиком, либо воюет с текущим CSS), нет русского, и главное — жёсткий контракт-конверт на все API. Это не виджет, это захват фронтенда, и в момент, когда клиенту понадобится что-то за пределами схемы, выхода нет.

Против json-editor: JSON Schema описывает данные, а не раскладку; ref-picker в его справочники, деньги, даты и русские подписи всё равно писать самому через кастомные редакторы — то есть дорогая часть остаётся, а 536 КБ приезжают.

Tabulator — единственная честная покупка в списке (виртуальный скролл и редактирование в ячейке — это реально больше дня работы, MIT, один файл, офлайн). Но на 30 пользователях и реестрах в сотни строк обычная `<table>` с серверной пагинацией в его же CSS лучше. Держать Tabulator как известный запасной вариант на случай «нужен Excel в браузере», не платить за него заранее.

Итого:
- `GET /api/meta/<entity>` → JSON: поля + ui + enum'ы + права текущего пользователя.
- `static/js/screen.js` — обычный ES-модуль, ~150 строк список + ~200 строк форма. Никакого бандлера. Кэш-бастинг — `?v=<pack_version>`.
- Один generic-роутер на FastAPI поверх сырого SQLite: `GET/POST/PUT/DELETE /api/e/<entity>`, параметры `page`, `sort`, `q`, `filter[<col>]`.

Новый справочник после этого = несколько строк в метатаблицах, ноль строк кода, ноль перезапусков.

### 2.2 Где потолок и три выхода из него (закладывать с первого дня)

Это то место, где ломаются все схемные движки. Выходы должны стоить дёшево и существовать сразу:

1. **Слоты в generic-шаблоне** (plugin outlets из Discourse): `<div data-outlet="entity.form.after"></div>`, `<div data-outlet="entity.list.toolbar"></div>`. Клиентский файл `ext/<client>/ui/*.js` вызывает `mount('entity.form.after', fn)`. Только добавление до/после, никогда `replace` — иначе обновление ядра молча сломает клиентский UI. Плюс режим отладки, подсвечивающий имена слотов прямо на странице: он сам себе скажет спасибо на третьем клиенте.
2. **`meta_entity.page_tpl`** — если заполнено, ядро отдаёт `ext/<client>/pages/<key>.html` вместо generic-шаблона, но API остаётся тот же generic. То есть «generic → руками» решается поэкранно, а не всё-или-ничего.
3. **Кодогенератор** (приём Refine Inferencer, и он стратегически вернее движка): `python -m tools.genscreen c_extinguishers` читает метаданные и пишет три файла — HTML, JS, роутер — в его текущем стиле и с его CSS. Дальше это обычный код проекта, правится руками, отлаживается в браузере, коммитится. У интерпретатора схемы есть потолок, у генератора — нет.

### 2.3 Условная логика без парсера и без eval

Не изобретать язык выражений. JSON-условие, ~40 строк интерпретатора на клиенте и **та же функция на сервере для валидации** (приём EspoCRM Dynamic Logic):
```json
{"all": [{"f": "f_7", "op": "eq", "v": "archived"},
         {"any": [{"f": "f_3", "op": "gt", "v": 0}]}]}
```
Операторы: `eq, ne, gt, lt, in, empty, notempty`. Всё. Один формат, два вычислителя, ноль зависимостей, `eval` нигде.

### 2.4 Когда декларативно, а когда писать руками

**Декларативно окупается**, если экран — плоский справочник/реестр (список + фильтр + форма + CRUD), их у клиента 5+, они похожи друг на друга, и их надо править на объекте без релиза. Это огнетушители, журналы инструктажей, реестры объектов, контрагенты, номенклатура СИЗ.

**Писать руками**, если:
- документ с табличной частью и расчётами (путевой лист: шапка + строки + итоги);
- нетривиальная печатная форма — печать всё равно идёт через его генератор DOCX, а не через HTML;
- мастер/анкета с ветвлением;
- ценность экрана в самом взаимодействии (двухпанельный вывод рисков договора с подсветкой цитат, сравнение редакций, редактор шаблонов).

**Практическое правило**: если ТЗ на экран умещается в одно предложение («реестр огнетушителей с фильтром по цеху и сроку перезарядки») — декларативно. Если нужен абзац — руками, а метаданные использовать только как источник справочных данных.

По деньгам: декларативный слой окупается начиная примерно с четвёртого справочника. До этого он проигрывает написанию страницы руками — и это надо честно себе сказать, чтобы не строить движок ради одного экрана.

## 3. Изоляция клиентских модулей против `git reset --hard` и `integrity.json`

Это главный вопрос, и он решается не дисциплиной, а **конструкцией: сделать так, чтобы клиентский файл физически не мог попасть в область действия обоих механизмов.**

### 3.1 Разделить корень кода и корень данных

```
C:\Program Files\PozhAI\app\        <- рабочее дерево git. Только код + базовые шаблоны + базовые JSON.
C:\ProgramData\PozhAI\              <- data-root. Ничего из этого git не видит.
    db\client.sqlite
    ext\<client>\                    <- клиентский пакет: hooks.py, ui\, pages\, templates\, pack.json
    uploads\  generated\  logs\  backups\
```
Путь к data-root задаётся переменной окружения или файлом рядом с exe, **не** файлом внутри дерева. На старте — жёсткая проверка:
```python
assert not Path(DATA_ROOT).resolve().is_relative_to(Path(REPO_ROOT).resolve()), \
    "data-root внутри рабочего дерева git — обновление уничтожит данные клиента"
```
и вторая — что `ext/` не внутри репозитория. Обе падают с внятным текстом, а не загадочно.

### 3.2 Генерировать `integrity.json` из `git ls-files`

Один ход, снимающий противоречие структурно: манифест целостности собирается на его машине при выпуске релиза **из списка файлов, которыми владеет git**. По построению он не может покрыть ни один клиентский файл, потому что клиентских файлов в git ядра нет. Ложных срабатываний из-за кастомизации не бывает в принципе, и проверка целостности при этом остаётся осмысленной — она по-прежнему ловит битую распаковку, недокачанное обновление и правку кода на месте.

### 3.3 Второй манифест — для расширений, с мягким отказом

`ext/<client>/pack.json`:
```json
{
  "pack": "pozhservice",
  "pack_version": "1.4.0",
  "core_min": "2.3.0",
  "core_max": "2.9.99",
  "files": {"hooks.py": "sha256:...", "ui/forms.js": "sha256:..."},
  "migrations": ["001_extinguishers", "002_deadlines"]
}
```
Политика принципиально **другая**, чем у ядра:

| | ядро (`integrity.json`) | пакет (`pack.json`) |
|---|---|---|
| расхождение хэшей | **приложение не стартует** | пакет отключается, ядро работает, в админке красный баннер, запись в лог |
| несовместимость версий | — | пакет отключается, баннер «пакет 1.4.0 требует ядро 2.3.0–2.9.99, установлено 3.0.1» |

Логика простая: расхождение в ядре означает недоверенный код — стартовать нельзя. Расхождение в пакете означает, что кто-то на объекте правил файл или обновление ушло вперёд — это надо громко показать, но валить работающую у 30 человек систему из-за отвалившегося справочника огнетушителей нельзя. Он один, он не приедет за 20 минут.

### 3.4 Обновление как транзакция

Автообновление должно стать пятишаговой процедурой вместо голого `git reset --hard`:

1. **Карантин.** `git status --porcelain`; если непусто — скопировать эти файлы в `backups\quarantine\<дата>\` и записать в лог WARNING. Никогда не уничтожать правки молча: рано или поздно он сам что-то поправит на сервере у клиента в 2 часа ночи.
2. **Бэкап БД.** `VACUUM INTO 'backups\pre-<version>.sqlite'` — один файл, штатный SQLite, ноль зависимостей. Плюс запомнить текущий `git rev-parse HEAD`.
3. **`git reset --hard` + миграции ядра.** Версия схемы — в `PRAGMA user_version` (приём Grist), миграции — список функций в одном модуле, применяются по возрастанию. Никакого alembic и никакой SQLAlchemy.
4. **Применение пакета.** Проверить `core_min/core_max`, прогнать миграции пакета, запустить генератор схемы (diff `meta_field` против `PRAGMA table_info`).
5. **Smoke-check.** 10–15 запросов: старт, логин, список по каждой зарегистрированной сущности, генерация одного DOCX, один вызов Ollama. Провалился — откат на запомненный ref и восстановление БД из бэкапа, приложение поднимается на старой версии, в лог и в баннер.

И отдельно — **предполётная проверка у него дома**, а не у клиента: команда, которая берёт копию БД и пакет каждого клиента (он их хранит у себя), прогоняет на них шаги 3–5 и печатает таблицу «клиент × результат». Это бедняцкий CI, но при 5–10 клиентах он снимает главный риск и стоит день работы.

### 3.5 Хуки: реестр на 60 строк, без pluggy

```
ext/pozhservice/hooks.py
  HOOKS = {
    'document.before_save':   [validate_inn],
    'letter.before_render':   [add_nlmk_requisites],
    'contract.after_analyze': [attach_playbook_notes],
    'prompt.extend':          [add_client_rules],     # клиентские правила прямо в промпт LLM
    'menu.items':             [extra_menu],
    'routes.register':        [make_router],          # возвращает APIRouter → app.include_router
    'permission.allowed':     [custom_acl],           # 'да'/'нет'/'не знаю', ядро агрегирует
  }
```
Загрузка — `importlib.util.spec_from_file_location` по пути из data-root на старте. Восемь хуков закрывают всё, что реально понадобится. `pluggy` — крошечная и безопасная зависимость, но собственный реестр это 60 строк, а установщик у него ломался от новых зависимостей: ноль новых пакетов побеждает.

**Чего не делать: Server Script в БД (Frappe).** Исполнение произвольного Python из строки таблицы на офлайн-сервере без песочницы — это и дыра, и конец истории с целостностью. Только декларативные правила.

### 3.6 Экспорт/импорт пакета — то, ради чего всё затевалось

Приёмы `bench export-fixtures` (Frappe), 2Pack (iDempiere) и платная serialization Metabase — все про одно, и это ему нужно независимо от монетизации:

```
python -m tools.pack export  -> ext/<client>/data/*.json
python -m tools.pack import  -> идемпотентное применение
```
Выгружаются все строки метатаблиц с `origin != 'core'` плюс справочные данные, помеченные как часть пакета. Получается версионируемый артефакт: настройка, сделанная мышкой на объекте у клиента, превращается в JSON, коммитится в репозиторий клиента, поднимается копией на его машине для отладки и откатывается. Без этого каждый выезд — невоспроизводимое событие, и на третьем клиенте начнётся расхождение форков.

## 4. Ролевые интерфейсы: минимальная работающая версия

Три таблицы, одна функция, одно правило.

```sql
CREATE TABLE role (key TEXT PRIMARY KEY, title TEXT NOT NULL, ord INTEGER DEFAULT 100);
CREATE TABLE user_role (user_id INTEGER NOT NULL, role_key TEXT NOT NULL,
                        PRIMARY KEY(user_id, role_key));
CREATE TABLE role_perm (
  role_key TEXT NOT NULL,
  object   TEXT NOT NULL,   -- 'entity:c_extinguishers' | 'field:addressees.f_9'
                            -- | 'action:contract_analyze' | 'query:expiring'
  level    TEXT NOT NULL,   -- 'none' | 'read' | 'read_own' | 'write' | 'admin'
  PRIMARY KEY(role_key, object)
);
```

Что делает эту версию рабочей, а не игрушечной:

1. **Права порождаются декларацией** (приём Flask-AppBuilder). Регистрируется сущность, действие или отчёт — ядро само заводит соответствующие `object` и показывает их в матрице «роль × объект» в админке. Отдельного списка прав, который вечно отстаёт от списка экранов, не существует.
2. **Одна точка проверки.** Все generic-роуты и все рукописные экраны зовут одну функцию `require(user, object, level)`. ~30 строк. Не проверить невозможно, потому что generic-роутер вызывает её сам.
3. **Меню выводится из прав, а не настраивается отдельно.** Сущность с `level='none'` просто не появляется. Это то, что делает «у каждой роли свой экран» почти бесплатным.
4. **Поля прячет сервер, а не JS.** При `field:<entity>.<col>` = `none` поле вырезается и из ответа `GET /api/meta/<entity>`, и из строк данных. Скрытие в браузере — не право доступа. Для его домена это нужно сразу: водитель и механик видят в путевом листе разное.
5. **Строчный уровень — один частный случай, не движок.** `meta_entity.owner_col` + уровень `read_own` → generic-запрос дописывает `AND <owner_col> = :user_id`. Это закрывает 90% («водитель видит свои путевые листы»). Формульные ACL уровня Grist не строить.
6. **На первом клиенте ровно три роли**: `admin`, `editor`, `viewer`. Матрицу из двенадцати ролей не рисовать — её попросят, но она никому не нужна.

Каскад «роль → экран → вкладка → поле» из iDempiere в полном виде избыточен; связка «объект + уровень» покрывает то же самое одной таблицей.

## 5. Что НЕ делать: красивое, но яд для одиночки

1. **Генерировать всё приложение из метаданных** (DocType Frappe, Application Dictionary iDempiere). У него 26 500 строк работающего кода. Метаслой обслуживает НОВЫЕ справочники и допполя к существующим сущностям; действующие функции остаются кодом. Переписывать ядро в метаданные — способ потерять год.
2. **Чистый EAV.** Явный отрицательный урок Corteza, на SQLite хуже, чем на Postgres.
3. **Генерация API/GraphQL в рантайме** (Twenty). Отладка становится невозможной в одиночку, выигрыш при его числе сущностей нулевой.
4. **Визуальный конструктор форм** (formio builder, Odoo Studio). Огромная поверхность, и он противоречит его же УТП: он продаёт разбор процессов и настройку, а не самообслуживание. Odoo не зря держит Studio платным и только в Enterprise — инструмент персонализации не отдаётся, отдаётся результат.
5. **Amis и любой фронтенд-фреймворк-захватчик.** 4,4 МБ, свой визуальный язык, свой контракт API, нет русского.
6. **Server/Client Script в БД.** Произвольный код из таблицы, без песочницы, на офлайн-сервере.
7. **Монкипатчинг и слияние классов** (`_inherit` Odoo, PoolMeta Tryton). В Python без большой команды это отладочный ад. Хуки честнее.
8. **Матрица конверсий типов полей** (Baserow). Запретить смену типа, предложить новое поле.
9. **BPMN-движок** (ELMA), реактивный граф биндингов (Appsmith), слоистые плейбуки (Ivo), аннотации-отношения (OpenContracts). Всё это верхняя граница подхода, а не цель.
10. **alembic, SQLAlchemy, Redis, pluggy — любые новые зависимости ради инфраструктуры.** `PRAGMA user_version` + список функций-миграций это ~80 строк. Установщик важнее элегантности.
11. **Docling/torch, Python-Redlines (предсобранный .NET-бинарь, извлекается в кэш, ловит антивирус на корпоративном Windows).** Если очень нужно — только отдельным опциональным модулем с graceful-фолбэком, и проверять на целевом сервере ДО обещаний клиенту.
12. **Две сборки (бесплатная/платная).** Один артефакт, флаги в конфиге. Два установщика при его установщике — смерть.
13. **Мультиарендность внутри одной БД.** Один клиент — один файл.
14. **Копировать код под GPL/AGPL** (Paperless-ngx, Dolibarr, SuiteCRM, ToolJet, Khoj, Documenso, Budibase). Модели данных и UX копировать никто не запрещает, код — нельзя при закрытой поставке. Безопасно брать: Grist и Datasette (Apache-2.0), Baserow-ядро, Tabulator, json-editor (MIT).
15. **Публичный плагин-маркетплейс.** Категория «Документооборот» в Битрикс24 живёт на 8–230 установках. Мёртвая земля.

## 6. Порядок внедрения

Ориентир — три недели чистого времени до состояния «новый клиент за дни».

**Шаг 0 (1 день, без него всё остальное на песке): развести корень кода и корень данных.** БД, `ext`, загрузки, логи — в `%ProgramData%`. `integrity.json` — генерировать из `git ls-files`. Две проверки-ассерта на старте. Это разрешает противоречие «клиентский код против манифеста» и стоит один день.

**Шаг 1 (2–3 дня): метатаблицы + генератор схемы + интроспектор.** Зарегистрировать `addressees` и ещё 2–3 существующие таблицы. Видимого эффекта нет, это фундамент.

**Шаг 2 (3–4 дня): generic CRUD API + generic список и форма.** Вот здесь появляется рычаг «неделя → час»: новый справочник клиента = строки в метаданных, ноль кода. **Если он успевает сделать только одно до следующего клиента — это шаги 1+2.**

**Шаг 3 (3–4 дня): пакет клиента.** `pack.json` с `core_min/core_max`, export/import метаданных в JSON, миграции через `PRAGMA user_version`, транзакция обновления с бэкапом, smoke-check и откатом. Это то, что не даёт превратиться в 10 расходящихся форков к третьему клиенту, и то, что делает его выезд воспроизводимым артефактом.

**Шаг 4 (2 дня): роли.** Три таблицы, `require()`, меню из прав. Заложить надо СЕЙЧАС, даже если пока все админы: дописать потом вчетверо дороже, а на втором клиенте «кладовщик не должен видеть договоры» встанет обязательно.

**Шаг 5 (2 дня): движок сроков.** Первое, что клиент УВИДИТ и за что заплатит. Утренний список «на этой неделе истекает 7 позиций» на демо продаёт лучше, чем ИИ, и не требует ни LLM, ни зависимостей.

**Шаг 6 (2 дня): хуки, слоты и `page_tpl`.** Именно сейчас, а не раньше: к этому моменту он уже знает, какие экраны реально вылезают за декларативный рендер, и расставит слоты по факту, а не по догадке.

**Дальше по потребности**: именованные SQL-отчёты (canned queries Datasette — на read-only соединении `file:...?mode=ro`), представления `meta_view`, `tools.genscreen`, Tabulator.

**Что даёт больше всего свободы на первом же новом клиенте** — шаги 0+1+2, примерно 6–8 дней. После них разговор на внедрении меняется качественно: «нужен реестр огнетушителей с полями X, Y, Z и фильтром по цеху» перестаёт быть задачей на неделю разработки и становится настройкой при клиенте, за встречу. Это и есть его УТП, положенное в механику.

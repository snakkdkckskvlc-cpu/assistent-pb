# Механика кастомизации везде одинакова и сводится к трём слоям: реестр расширений с хуками (ядро не знает о клиенте), слой метаданных, описывающий поля/формы/права данными, и экспорт этих метаданных в версионируемый файл, переживающий обновление ядра. Для FastAPI + SQLite + ванильного JS одним человеком воспроизводимы четыре вещи и они дают ~80%: реестр плагинов в духе Datasette/pluggy (каталог plugins/<client>/ + 6–8 хуков), дельта-переопределения в духе Frappe Property Setter (таблица «сущность, поле, свойство, значение»), sidecar-таблица доп. полей в духе Dolibarr/Битрикса (ALTER TABLE ADD COLUMN в SQLite мгновенный, backfill не делается) и слоёный deep-merge JSON-конфиг в духе EspoCRM для раскладки форм и видимости по ролям. По схеме данных для «полей на лету» на SQLite вердикт: чистый EAV не брать (отрицательный урок Corteza), JSON-колонка + таблица-схема (Tryton fields.Dict, Axelor MetaJsonField) — только для редко-фильтруемых атрибутов, всё по чему ищут и сортируют — реальные колонки в отдельной таблице `<entity>_extra`; компромисс — JSON + virtual generated column + индекс по json_extract. Три дешёвых приёма-множителя: технические имена колонок вместо человеческих (Baserow `field_{id}` — спасает от переименований и русских подписей), генерация ALTER TABLE из diff метаданных против `PRAGMA table_info` (идея Twenty, ~100 строк, снимает нужду в alembic), версия клиентского пакета в `PRAGMA user_version` (Grist). Ближайший к его стеку проект — Grist: Python + один файл SQLite, пользовательские таблицы настоящие, рядом метатаблицы `_grist_Tables_column`; файл `sandbox/grist/schema.py` стоит прочитать целиком как готовый чек-лист атрибутов поля.

## Frappe Framework / ERPNext — MIT (Frappe Framework); ERPNext — GPLv3
https://github.com/frappe/frappe

**Что:** Метаданный веб-фреймворк на Python, поверх которого написан ERPNext. Сущности, формы, права, отчёты и печатные формы описаны записями DocType, лежащими в самой БД.

**Умный приём:** DocType — единственный примитив: одна запись порождает реальную таблицу `tab<Name>` с реальными колонками, JSON-описание формы, REST-эндпоинты, права и вид списка. Кастомизация клиента сделана тремя механизмами ПОВЕРХ, а не форком: (а) Custom Field — новая запись, которая делает ALTER TABLE и втыкается в форму по `insert_after`; (б) Property Setter — дельта вида (doctype, fieldname, property, value), переопределяющая ОДНО свойство ядрового поля (label, reqd, hidden, options, in_list_view) не трогая исходный DocType-JSON; (в) Client Script / Server Script — код, лежащий в БД записью, а не файлом. Сверху hooks.py в отдельном app: `doc_events` (before_save/on_submit по имени доктайпа), `override_doctype_class`, `override_whitelisted_methods`, `extend_bootinfo`, `required_apps`. Апгрейд-безопасность: `bench export-fixtures` выгружает Custom Field и Property Setter в `fixtures/*.json` внутри клиентского приложения, `bench migrate` идемпотентно применяет — доработки клиента живут отдельным git-репозиторием, а не патчами к ядру.

**Применимо:** Property Setter — самая копируемая идея во всём исследовании и точно под его УТП. Таблица `ui_override(client_id, entity, field, prop, value)`, читаемая при сборке описания формы, даёт «настройка под конкретную компанию без правки кода» за 3–5 дней. Fixtures = ручка экспорта этой таблицы в JSON, который кладётся в папку клиента и коммитится. Сам DocType-подход (генерировать ВСЁ из метаданных) для него слишком радикален: у него 26 500 строк написанного кода, ядро переписывать не надо — брать только слой переопределений.

**Трудоёмкость:** неделя

## Odoo (Community + Studio) — LGPLv3 (Community); Odoo Studio — проприетарный (Enterprise)
https://github.com/odoo/odoo

**Что:** Крупнейший модульный ERP на Python/PostgreSQL. Приложение собирается из сотен модулей, каждый — папка с `__manifest__.py`, моделями, XML-видами и данными.

**Умный приём:** Три независимых уровня наследования. (1) `_inherit` — клиентский класс с тем же `_name` мержится в один ORM-класс: можно добавить поле, обернуть метод через super(), переопределить домен; ядро об этом не знает. (2) `_inherits` — делегирование (product.product держит ссылку на product.template и прозрачно проксирует его поля). (3) Наследование ВИДОВ через XPath: клиентский модуль пишет `<xpath expr="//field[@name='partner_id']" position="after">...</xpath>`, и форма ядра патчится декларативно — при обновлении ядра патч переприменяется к новой версии формы, а не затирает её. Реестр модулей — граф зависимостей из `depends`, топосорт, послойная сборка финального класса. Динамические поля: запись в `ir.model.fields` со `state='manual'` и именем `x_*` → при старте ORM дочитывает эти записи и создаёт настоящую колонку в PostgreSQL. То есть «поле из кода» и «поле из Studio» — один и тот же механизм, разный только источник описания.

**Применимо:** XPath-патчинг видов — прямой ответ на «как менять форму под каждого клиента, не форкая HTML». У него ванильный JS без сборки, значит формы можно хранить декларативно (JSON или HTML-шаблон), а клиентские правки — списком операций (селектор + before/after/replace/attributes) и собирать финальный шаблон на сервере перед отдачей. Это его бизнес-модель, положенная в механику. Питоновское `_inherit` с мержем классов ему не нужно и опасно (монкипатчинг сложно отлаживать в одиночку) — хуки честнее.

**Трудоёмкость:** неделя

## Dolibarr — GPLv3+
https://github.com/Dolibarr/dolibarr

**Что:** ERP/CRM на PHP для малого бизнеса, принципиально без сборщиков и тяжёлых зависимостей: залил файлы — работает. Ближе всего по духу к «прагматичной системе без инфраструктуры».

**Умный приём:** Три вещи. (1) Extrafields — самое прагматичное решение динамических полей из всех: ОПРЕДЕЛЕНИЯ в одной таблице `llx_extrafields` (elementtype, name, label, type, param, pos, perms, list, required), а ЗНАЧЕНИЯ — в sidecar-таблице на сущность `llx_societe_extrafields(rowid, tms, fk_object, <колонка на каждое доп. поле>)`, колонки заводятся настоящим ALTER TABLE. Это не EAV: значения типизированы, индексируются, UNIQUE работает, чтение — обычный JOIN один-к-одному. (2) Модуль = один класс-дескриптор `modXxx.class.php` с массивами: пункты меню, права, словари, какие части ядра расширить, какие таблицы создать. Установка = запись в конфиг, никакой сборки. (3) Хуки: ядро в ключевых точках зовёт `$hookmanager->executeHooks('formObjectOptions', $params, $object, $action)`, и любой модуль, объявивший себя на этот контекст, вклинивается, включая подмену вывода через `reshook`.

**Применимо:** Sidecar-таблица + ALTER TABLE — лучший вариант на SQLite и то, что ему стоит взять по умолчанию. ADD COLUMN в SQLite это O(1), только правка записи схемы, backfill не делается. Значения типизированы, индексы обычные, отчёты пишутся руками на SQL без json_extract. Отдельная таблица (а не колонки в основной) нужна затем, чтобы его собственные миграции ядра никогда не конфликтовали со схемой клиента. Ограничения SQLite учесть: DROP COLUMN только с 3.35+, RENAME COLUMN с 3.25+, смена типа невозможна — поэтому «удаление поля» делать логическим флагом в метаданных, а не DDL. Класс-дескриптор модуля — готовый формат для его клиентских пакетов.

**Трудоёмкость:** день

## Tryton — GPLv3+
https://github.com/tryton/trytond

**Что:** Потомок TinyERP, зрелый Python-фреймворк с очень чистой модульной архитектурой; известен строгостью и малым количеством магии по сравнению с Odoo.

**Умный приём:** (1) PoolMeta — расширение по ИМЕНИ, а не по импорту: клиентский модуль пишет `class Party(metaclass=PoolMeta): __name__ = 'party.party'` и регистрирует класс в Pool; Pool собирает MRO из всех модулей, объявивших это имя, в порядке зависимостей. Расширение не импортирует ядровый класс, ядро не знает о расширении — циклических импортов нет в принципе. (2) `fields.Dict` + `DictSchemaMixin` — поле-словарь в одной колонке, но со СХЕМОЙ, живущей обычной таблицей-моделью (ключ, тип, домен допустимых значений, переводимая подпись). Получаются «атрибуты на лету» с валидацией и человеческими подписями, без EAV и без ALTER TABLE. (3) `__register__` — модель сама мигрирует свою таблицу при обновлении через TableHandler; миграция лежит рядом с моделью, а не в отдельной папке версий.

**Применимо:** `fields.Dict` — прямой готовый прототип «JSON-колонка + таблица-схема» на SQLite: колонка `extra JSON` в основной таблице + таблица `field_schema(entity, key, type, label, options_json, ord, required, role_visible)`. Читается легко, версионируется одним JSON-файлом, не плодит таблиц, идеально для редких атрибутов вроде «объект НЛМК: цех, ответственный, категория помещения». Минус на SQLite — фильтрация и сортировка требуют `json_extract`; лечится virtual generated column + индексом по нему. Идею «миграция живёт в модели» тоже стоит взять: у него нет alembic и заводить его нельзя.

**Трудоёмкость:** день

## Axelor Open Platform / Open Suite — AGPLv3
https://github.com/axelor/axelor-open-platform

**Что:** Java/Hibernate-платформа с ERP-набором поверх; продаётся именно как low-code — Studio для полей и форм, BPM для процессов.

**Умный приём:** Доведённый до предела гибрид JSON-колонки и метаданных. Модель объявляет `jsonAttr="true"` (или строковое поле с `json="true"`), и ВСЕ кастомные поля клиента складываются в эту одну колонку. Описание каждого поля — запись `MetaJsonField`: имя, тип, виджет, порядок, ширина, условие видимости (выражение), required-выражение, домен для связей, вкладка. Дальше самое интересное: `MetaJsonModel` позволяет завести целую НОВУЮ сущность без единой миграции — её записи лежат в общей таблице `MetaJsonRecord` с JSON-нагрузкой, и такие сущности участвуют в связях (json-many-to-one, json-one-to-many с каскадами и orphan removal). Studio и BPM-конструктор пишут в те же самые метатаблицы, что разработчик руками — единый источник истины, а не параллельная реальность.

**Применимо:** Показывает верхнюю границу подхода и реалистичную цель для него: одна таблица `custom_record(id, model_key, client_id, data JSON, created_at)` + метатаблицы `custom_model` / `custom_field`, и клиентские справочники («журнал инструктажей», «реестр огнетушителей», «график проверок») заводятся из админки за минуты при внедрении, без релиза. Ключевой приём к копированию — хранить в описании поля ВЫРАЖЕНИЯ видимости и обязательности, а не булевы флаги: это то, что превращает форму из статичной в умную без кастомного JS. Минус честно: без реальных колонок сложные отчёты и JOIN'ы больно, поэтому JSON-сущности — только для справочников и журналов, не для того, что ляжет в аналитику.

**Трудоёмкость:** неделя

## iDempiere — GPLv2
https://github.com/idempiere/idempiere

**Что:** Потомок Compiere/ADempiere, Java + OSGi. Самая радикальная из живых реализаций идеи «приложение как данные».

**Умный приём:** Application Dictionary: ВСЁ приложение описано записями в таблицах `AD_Table`, `AD_Column`, `AD_Window`, `AD_Tab`, `AD_Field`, `AD_Process`, `AD_Reference`, `AD_Val_Rule`. UI не пишут — его генерируют из словаря на лету. Правка под клиента = INSERT/UPDATE в словарь. Перенос между средами — 2Pack: `PackOut` выгружает выбранные записи словаря (окна, поля, процессы, справочные данные, роли) в один XML внутри zip; `PackIn` применяет. Zip кладут в `META-INF` собственного OSGi-плагина, и активатор (`Incremental2PackActivator`) при старте применяет только те версии, которые ещё не применялись — клиентская доработка становится версионируемым артефактом с номером версии и идемпотентной установкой, ставящимся рядом с ядром, а не в него. Права выстроены каскадом отдельными таблицами: роль → доступ к окну → к вкладке → к полю → к процессу, поэтому у каждой роли буквально свой экран, собранный из словаря без единого if в коде.

**Применимо:** 2Pack — готовый ответ на вопрос про версионирование клиентских доработок при обновлении ядра. Минимальная версия для него: ручка `GET /admin/export-customization`, отдающая JSON со всеми записями его метатаблиц для данного клиента плюс `pack_version`; при старте приложение сравнивает версию в файле с записанной в БД и применяет разницу транзакцией. Каскад прав «роль → экран → вкладка → поле» стоит копейки (три таблицы связей) и полностью закрывает вопрос «у каждой роли свой интерфейс» — на его 30 пользователях это реально работающая, а не теоретическая штука. Полноценный Application Dictionary одному человеку не потянуть и не нужно.

**Трудоёмкость:** неделя

## EspoCRM — AGPLv3
https://github.com/espocrm/espocrm

**Что:** CRM на PHP, целиком построенная на слоёных JSON-метаданных. Небольшая читаемая кодовая база — реально прочитать за вечер и понять устройство.

**Умный приём:** Рекурсивный merge JSON-метаданных по слоям: core → module → custom. Ядро кладёт `Resources/metadata/entityDefs/Account.json`, клиентская папка `custom/Espo/Custom/Resources/metadata/entityDefs/Account.json` содержит ТОЛЬКО дельту, слои сливаются рекурсивно (объекты мержатся, а не заменяются целиком), результат кешируется. Тем же способом переопределяются `layouts` (какие поля в какой колонке detail-формы, что в списке, что в фильтре), `clientDefs` (какой JS-view подставить), `aclDefs`, `selectDefs`, `pdfDefs`. Отдельно — Dynamic Logic: условная логика формы описана декларативно JSON-условием («поле обязательно, если статус = X»), и оно проверяется И на клиенте (показать/скрыть/заблокировать), И на сервере (валидация), из одного описания. Entity Manager заводит новую сущность целиком из UI. Права ролевые, с гранулярностью до поля (own/team/all × read/edit).

**Применимо:** Слоёный JSON ложится на его бизнес-модель точнее всего остального: `base/*.json` в репозитории продукта, `clients/pozhservice/*.json` — в репозитории клиента, deep-merge при старте, кеш в память. Не нужны ни БД, ни ORM, ни зависимости — установщик не заметит. Dynamic Logic — то, что делает форму умной без единой строки клиентского JS: на его ванильном фронте интерпретатор условий это ~150 строк, а на бэке та же функция для валидации. Гранулярность прав до поля важна для его домена (акты, договоры, путевые листы: водитель видит не то, что механик). Читать: `application/Espo/Core/Utils/Metadata.php` и структуру `Resources/metadata/`.

**Трудоёмкость:** неделя

## Grist (grist-core) — Apache 2.0
https://github.com/gristlabs/grist-core

**Что:** Гибрид таблицы и БД от Grist Labs. Каждый документ — ОДИН файл SQLite; серверная часть на Node, движок формул — Python в песочнице.

**Умный приём:** Технически это самый близкий к его стеку проект во всём списке. Документ `.grist` — файл SQLite, где пользовательские таблицы лежат НАСТОЯЩИМИ таблицами с настоящими типизированными колонками, а рядом метатаблицы, описывающие, что это за таблицы, как их показывать и кому: `_grist_Tables`, `_grist_Tables_column` (colId, type, label, widgetOptions, isFormula, formula, parentPos, untieColIdFromLabel), `_grist_Views`, `_grist_Views_section`, `_grist_Views_section_field`, `_grist_ACLRules`, `_grist_ACLResources`. Схема всех метатаблиц объявлена ОДНИМ питоновским файлом `sandbox/grist/schema.py`. Версия формата — в `PRAGMA user_version`, есть цепочка миграций документа при открытии старого файла новым кодом. Добавление колонки пользователем = ALTER TABLE + запись в `_grist_Tables_column` в одной транзакции. ACL — тоже строки в метатаблице, с условиями-формулами на уровне строк и колонок (`user.Access == 'owner'`, `rec.status == 'draft'`).

**Применимо:** Прямо его связка: Python + один файл SQLite + браузер, и задача «поля определяются на лету» там уже решена в проде. Конкретное действие: открыть `sandbox/grist/schema.py` и выписать, какие ровно атрибуты колонки они сочли необходимыми — это готовый выстраданный чек-лист для его таблицы метаданных, изобретать не надо. Второе к копированию — `PRAGMA user_version` как механизм миграции клиентских БД: дешевле alembic, ноль новых зависимостей (критично, установщик хрупкий), и естественно ложится на «у каждого клиента свой файл БД». Третье — `untieColIdFromLabel`: техническое имя колонки отвязано от подписи (та же идея, что в Baserow).

**Трудоёмкость:** неделя

## Directus — BSL 1.1 (до v10 — GPLv3)
https://github.com/directus/directus

**Что:** Headless-платформа поверх ЛЮБОЙ существующей SQL-базы (включая SQLite): подключается к готовой БД, интроспектит её и даёт админку плюс REST/GraphQL API.

**Умный приём:** Инверсия по сравнению со всеми остальными: источник истины — РЕАЛЬНАЯ схема БД, а не метаданные. Directus интроспектит существующие таблицы и связи, а системные таблицы `directus_collections` / `directus_fields` / `directus_relations` хранят только НАДСТРОЙКУ. У каждого поля две раздельные половины: `schema` — то, что в БД (тип, nullable, default, длина) и `meta` — то, что в UI (interface, options, display, width, note, conditions, sort, hidden, readonly, переводы). Отсюда главное свойство: Directus можно снести, и останется нормальная база данных, с которой работают обычным SQL. Плюс правила доступа (`directus_permissions`) с фильтрами по полям и по строкам, привязанные к ролям.

**Применимо:** Самая дешёвая и самая правильная философия для его случая — он УЖЕ работает с SQLite без ORM, то есть напрямую со схемой. Разделение «schema vs meta» снимает главный риск динамических полей: превращение БД в помойку, где без приложения ничего не понять. Минимальная версия на выходные: обычные таблицы как есть + ОДНА таблица `field_meta(table_name, column_name, label, widget, options_json, ord, required, hidden, role_visibility)`, наполняемая руками при внедрении у клиента, и генератор формы, читающий `PRAGMA table_info` + эту таблицу. Даёт больше всего пользы на вложенный час из всего списка. Сам Directus ему не подходит (Node.js запрещён), брать надо идею.

**Трудоёмкость:** день

## Baserow — MIT (core); premium/enterprise-модули — проприетарные
https://gitlab.com/baserow/baserow

**Что:** Open-source альтернатива Airtable на Django + PostgreSQL. Пользователь создаёт таблицы и поля из интерфейса, под капотом — настоящие таблицы и колонки.

**Умный приём:** Каждое пользовательское поле — реальная колонка PostgreSQL с ТЕХНИЧЕСКИМ именем `field_{id}`, а человеческое имя живёт только в метатаблице. Отвязка технического имени от отображаемого одним ходом решает три проблемы: переименование поля бесплатно (UPDATE одной строки метаданных, никакого DDL), одинаковые подписи у разных полей допустимы, не-ASCII и любые символы в подписи допустимы. Django-модель таблицы генерируется динамически в рантайме из метаданных и кешируется. Типы полей — плагины: класс `FieldType` с методами «как хранить» (описание колонки), «как валидировать», «как отдать в API», и — самое ценное — матрица конверсий при СМЕНЕ типа поля (что делать со значениями, если текст превращают в число или в список). Всё расширяется сторонним плагином без правки ядра.

**Применимо:** Приём `field_{id}` вместо человеческого имени он может украсть за час, и для русскоязычных подписей полей это фактически обязательно — иначе получит колонки транслитом или в кириллице и боль при первом же «переименуйте это поле». `FieldType` как класс с методами (sql_type / validate / coerce / render) естественно ложится и на его бэк, и на ванильный JS: один реестр типов полей на сервере, зеркальный на клиенте, добавление нового типа не трогает ядро форм. Матрицу конверсий типов копировать не надо — на его масштабе достаточно запретить смену типа и предложить создать новое поле.

**Трудоёмкость:** день

## SuiteCRM / SugarCRM CE — AGPLv3
https://github.com/salesagility/SuiteCRM

**Что:** Ветеран отрасли (PHP), выросший из SugarCRM. Интересен не функциональностью, а тем, как за 15+ лет решили проблему «клиент допилил систему, а мы выпустили обновление».

**Умный приём:** Два приёма, оба чисто про апгрейд. (1) Sidecar-таблица `<module>_cstm` с ключом `id_c`: все кастомные поля клиента лежат в ОТДЕЛЬНОЙ таблице, ядро при обновлении меняет только свою — конфликта схем не бывает по построению. (2) Каталог `custom/` и Extension framework: любой файл ядра может быть переопределён одноимённым файлом в `custom/`, а разрозненные куски определений (vardefs, языковые строки, пункты меню, логические хуки) кладутся ОТДЕЛЬНЫМИ файлами в `custom/Extension/modules/<Module>/Ext/Vardefs/*.php` и «компилируются» в один сводный файл при Repair — то есть двое разных внедренцев могут добавить свои правки одному модулю и не подраться за один файл. Доработка ставится Module Loader'ом как zip с манифестом: версия пакета, диапазон совместимых версий ядра, список файлов, скрипты install/uninstall — у клиентской доработки есть версия и деинсталлятор.

**Применимо:** Манифест доработки — ровно то, чего ему не хватает, чтобы бутиковые внедрения не превратились через год в 10 расходящихся форков. Начать можно вообще без кода: в каждом клиентском пакете `manifest.json` с `pack_version`, `core_version_min`, `core_version_max`, списком файлов и списком применённых миграций; при старте приложение проверяет совместимость и отказывается стартовать с внятным сообщением, а не падает загадочно. Приём «клиентские куски отдельными файлами, которые сливаются при сборке» — прямой аналог того, что EspoCRM делает merge'ем JSON, только на файлах; ему хватит одного из двух.

**Трудоёмкость:** день

## Corteza (Low Code) — Apache 2.0
https://github.com/cortezaproject/corteza

**Что:** Low-code платформа на Go (позиционируется как открытая альтернатива Salesforce): модули, страницы, автоматизации — всё создаётся из интерфейса.

**Умный приём:** Ценен как ОТРИЦАТЕЛЬНЫЙ пример, разобранный публично. По умолчанию — чистый EAV: значения записей лежат в `compose_record_value(record_id, name, place, value, ref)`, одна таблица на данные всех «модулей» всех приложений; схема модуля — в `compose_module_field`. Это дало мгновенный старт и полную динамику, а потом упёрлось в производительность, фильтрацию, сортировку и отчётность. Главное: они признали проблему и добавили «Customizing Record Storage» — маппинг модуля на РЕАЛЬНУЮ таблицу с реальными колонками, с кодеками кодирования значений на каждое поле, так что один и тот же прикладной слой умеет работать и через EAV, и через нормальную таблицу. **Применимо:** Главный вывод — не повторять: на SQLite чистый EAV убьёт всё, что связано с отчётами и фильтрами (каждое поле в WHERE = отдельный JOIN или self-join, планировщик SQLite сдаётся на этом быстрее PostgreSQL). Практическое правило, вытекающее из их истории: EAV допустим только для редко читаемых и редко фильтруемых атрибутов; всё, по чему ищут, сортируют или строят отчёт, — реальная колонка в sidecar-таблице. Page builder «страница = блоки с ролевой видимостью» — хорошая дешёвая модель для его вопроса про интерфейс под роль: таблица `page_block(page, type, config_json, ord, roles)` и рендер по ней.

**Трудоёмкость:** не стоит

## Twenty CRM — AGPLv3
https://github.com/twentyhq/twenty

**Что:** Современная open-source CRM (TypeScript/NestJS/PostgreSQL), альтернатива Salesforce. Интересна тем, что модель данных там — рантайм-сущность, а не код.

**Умный приём:** Схема на арендатора: каждый workspace получает СВОЮ PostgreSQL-схему, а форма её объектов целиком генерируется в рантайме из метабазы (`objectMetadata`, `fieldMetadata`, `relationMetadata`), которая физически лежит в отдельной базе. Из метаданных на лету собираются не только формы, но и GraphQL-типы, фильтры, сортировки и резолверы. Самое полезное — конвейер `workspace-migration`: изменение метаданных не применяется напрямую, а порождает описание миграции, которое затем транслируется в DDL к схеме конкретного арендатора. Разведение «метаданные» и «данные» по разным базам делает возможным атомарно откатить неудачное изменение модели.

**Применимо:** «Схема на клиента» у него по сути уже есть — отдельный файл SQLite на каждое внедрение. Ценная и дешёвая идея — генерировать миграции из diff'а метаданных, а не писать руками: сравнить «желаемое описание полей клиента» (JSON в его пакете) с фактическим `PRAGMA table_info(<table>)` и сгенерировать нужные ALTER TABLE ADD COLUMN. На SQLite это ~100 строк, ноль зависимостей, и полностью снимает боль обновления баз у 10 разных клиентов с 10 разными наборами полей. Генерацию API в рантайме копировать НЕ надо — для одного человека это ловушка: отладка становится невозможной, а выигрыш нулевой при его числе сущностей.

**Трудоёмкость:** неделя

## Datasette (+ pluggy) — Apache 2.0
https://github.com/simonw/datasette

**Что:** Инструмент для публикации и исследования SQLite-баз: один автор, Python, SQLite, серверный HTML без фронтенд-сборки. Единственный проект в списке ровно его масштаба и ровно его стека.

**Умный приём:** Расширяемость через pluggy (тот же механизм, что в pytest): файл `hookspecs.py` объявляет точки расширения декоратором `@hookspec`, плагин реализует одноимённые функции с `@hookimpl`. Регистрация — либо через `[project.entry-points.datasette]` в pyproject.toml для устанавливаемых пакетов, ЛИБО просто .py-файлом, положенным в каталог `--plugins-dir` — то есть одноразовый плагин под одну установку не требует упаковки вообще. Хуки покрывают весь жизненный цикл: `prepare_connection` (зарегистрировать SQL-функции), `register_routes` (свои URL), `extra_template_vars`, `render_cell` (как отрисовать значение ячейки), `menu_links`, `table_actions`, `startup`. Ключевой приём — `permission_allowed` как ХУК с трёхзначным ответом: права не зашиты в ядро, любой плагин отвечает «да / нет / не знаю», и ядро агрегирует. Плюс canned queries — именованные SQL-запросы из YAML-конфига, которые автоматически получают форму с параметрами и свой URL.

**Применимо:** Самый прямой и дешёвый ответ на вопрос «как добавить модуль клиенту, не трогая ядро» для FastAPI. Каталог `plugins/<client>/`, автозагрузка при старте, набор из 6–8 хуков: `register_routes` → возвращает `APIRouter` (FastAPI включает его через `app.include_router`), `menu_items`, `on_document_saved`, `extend_prompt` (важно для его LLM-части — клиентские правила прямо в промпт), `permission_allowed`, `render_field`. pluggy — крошечная зависимость без транзитивных, установщик переживёт; если и одну добавлять страшно, свой реестр хуков это 60 строк на `importlib` + словарь списков колбэков. Canned queries стоит украсть целиком: YAML/JSON с именованными SQL-запросами, из которых автоматически строится форма параметров и таблица результата — это «отчёты под клиента» без релиза, а у него домен с бесконечными реестрами и журналами.

**Трудоёмкость:** день

## Битрикс24 / 1С-Битрикс (механизм пользовательских полей UF) — закрытый (проприетарный), но структура БД и API документированы производителем
https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=43&LESSON_ID=3496

**Что:** Закрытая, но подробно документирующая свои внутренности российская платформа. Включён не как конкурент (заказчик с ней не конкурирует), а как отработанная на миллионах установок схема хранения пользовательских полей.

**Умный приём:** Трёхчастный гибрид, а не одна схема. ОПРЕДЕЛЕНИЯ полей — в `b_user_field` (ENTITY_ID, FIELD_NAME вида `UF_CRM_...`, USER_TYPE_ID, MULTIPLE, MANDATORY, SORT, SETTINGS). **Применимо:** Три вывода прямо в его схему данных.

# Главный вывод: почти всё поле low-code (Appsmith, Budibase, ToolJet, Directus, NocoDB, Baserow) требует Node.js, Docker и Postgres/Mongo/Redis — то есть отпадает по стеку целиком, и годится только как источник идей. Но есть ровно один проект, который проходит его ограничения буквально: Amis от Baidu — Apache-2.0, подключается двумя тегами (sdk.min.js ~1.9 МБ + sdk.min.css ~2.5 МБ), рисует полный CRUD-экран из JSON-объекта, не требует ни npm, ни новых pip-зависимостей, значит НЕ трогает его хрупкий установщик; бэкенду нужно лишь отдавать конверт {"status":0,"msg":"","data":{...}}, что на FastAPI пишется за час. Второй кандидат, если Amis кажется тяжёлым — @json-editor/json-editor (MIT, 536 КБ, ноль зависимостей, один тег), который делает форму из JSON Schema, и formio.js, у которого в открытой части есть ещё и drag-and-drop конструктор форм — то есть справочник под клиента может собрать не он, а сам клиент. Из Python-мира к нему применимы sqladmin (BSD-3, Jinja+Tabler, монтируется в его FastAPI, без Node) и Piccolo Admin (MIT, готовый фронт лежит внутри wheel, есть механизм «custom forms» — регистрируешь Pydantic-модель и получаешь экран); FastAPI-Admin отпадает жёстко — он требует Redis и Tortoise ORM. Идея, которую стоит украсть целиком, — не у JS-рендереров, а у Django Admin и Refine Inferencer: описывать каждый клиентский справочник одним Python-словарём (поля, типы, фильтры, права) и либо интерпретировать его в рантайме одним generic-роутером, либо один раз генерировать из него обычную HTML-страницу и дальше править руками. Мой ответ на его вопрос №5: свои 300 строк писать не надо — надо написать ~150 строк generic-таблицы + один decl-словарь на справочник, а формы отдать json-editor; это и есть рычаг «неделя → час», а Amis держать как запасной вариант под сложные составные экраны.

## Amis (baidu/amis) — Apache-2.0
https://github.com/baidu/amis

**Что:** Low-code фронтенд-фреймворк от Baidu: описываешь страницу JSON-объектом, он рендерит её целиком — формы, таблицы с пагинацией, фильтры, диалоги, вкладки, загрузка файлов. 18.9k звёзд, живой (последний пуш март 2026).

**Умный приём:** Есть отдельная сборка «SDK version», которая работает БЕЗ npm/webpack — ровно как jQuery. Вербатим из их доков:

<link rel="stylesheet" href="sdk.css" />
<div id="root" class="app-wrapper"></div>
<script src="sdk.js"></script>
<script>
let amis = amisRequire('amis/embed');
let amisJSON = {
  type: 'page',
  title: 'Форма',
  body: {
    type: 'form', mode: 'horizontal', api: '/saveForm',
    body: [
      {label: 'Name', type: 'input-text', name: 'name'},
      {label: 'Email', type: 'input-email', name: 'email'}
    ]
  }
};
let amisScoped = amis.embed('#root', amisJSON);
</script>

Второй умный ход — жёсткий контракт с бэкендом: любой API обязан отдавать конверт {"status": 0, "msg": "", "data": {...}}, где status=0 значит успех. Компонент type:'crud' сам шлёт page/perPage и ждёт в data поля items и total. То есть весь протокол между фронтом и бэком — это ОДНА функция-обёртка на FastAPI, и после неё любой новый экран = новый JSON, ноль JS.

**Применимо:** Единственный из всего списка, кто проходит его ограничения буквально. Ноль Node.js, ноль сборки, ноль НОВЫХ PIP-ЗАВИСИМОСТЕЙ — а значит не трогает его хрупкий установщик, что здесь важнее всего остального. Файлы (sdk.min.js ~1.9 МБ, sdk.min.css ~2.5 МБ, плюс iconfont/helper.css) кладутся в его static/ и работают полностью офлайн — CDN не нужен. Схему экрана можно хранить прямо в его SQLite как TEXT-поле и отдавать per-client — то есть «надстройка под каждую компанию» становится строкой в таблице, а не веткой в git. Два честных минуса: (1) размер CSS великоват и стиль у него свой — он либо примет вид Amis, либо будет воевать с его текущим CSS, изолируй через отдельную страницу/iframe; (2) русского в комплекте нет, но подписи и так идут из его JSON, так что это не проблема — проблема только во встроенных строчках («Submit», «No data»), их надо переопределять точечно.

**Трудоёмкость:** день

## fastapi-amis-admin — Apache-2.0
https://github.com/amisadmin/fastapi-amis-admin

**Что:** Мост между FastAPI и Amis: питоновский фреймворк админки в духе Django-admin, который по моделям SQLModel/SQLAlchemy сам генерирует и REST-эндпоинты, и Amis-схему интерфейса. Чистый Python, фронт рендерится готовым Amis SDK.

**Умный приём:** Внутри лежит подпакет fastapi_amis_admin.amis — Pydantic-модели ВСЕХ компонентов Amis. То есть схему экрана ты пишешь не как сырой dict, а типизированно, с автодополнением и валидацией в IDE: Page(body=Form(api=..., body=[InputText(name='inn', label='ИНН')])). Это снимает главную боль JSON-подхода — «опечатался в имени компонента, узнал в браузере». Плюс явно поддерживает SQLite через 'sqlite+aiosqlite:///base.db', и монтируется в существующее FastAPI-приложение через site.mount_app(app).

**Применимо:** Целиком брать не стоит: автогенерация CRUD завязана на SQLModel/SQLAlchemy, а у него SQLite БЕЗ ORM — тащить ORM ради админки значит ломать архитектуру и добавлять тяжёлую зависимость в тот самый установщик. А вот подпакет со схемами — можно вытащить идею и написать свои 20-30 dataclass'ов под те компоненты, которые он реально использует (форма, поле, таблица, колонка, кнопка). Это ~200 строк Python и полная типобезопасность описания экранов. Проект слегка подзастыл (последний пуш декабрь 2025), брать его как рантайм-зависимость рискованно, а как образец — отлично.

**Трудоёмкость:** неделя

## @json-editor/json-editor — MIT
https://github.com/json-editor/json-editor

**Что:** Библиотека, которая берёт JSON Schema и генерирует из неё HTML-форму. 4.9k звёзд, живой (пуш июль 2026), 536 КБ в минифицированном виде.

**Умный приём:** Ноль зависимостей — цитата из README: «JSON Editor has no dependencies. It only needs a modern browser». Один тег <script>, дальше new JSONEditor(element, {schema: {...}}) и editor.getValue(). Умеет то, что в самописном решении съест недели: вложенные объекты, массивы с кнопками add/remove/переупорядочить, oneOf/anyOf (переключатель типа записи), зависимости между полями, встроенную валидацию по схеме, и темы под bootstrap3/4/5 или голый HTML. Ключевое отличие от Amis: он делает ТОЛЬКО форму и не навязывает ни архитектуру, ни протокол API — вставляется в его существующую страницу как обычный виджет.

**Применимо:** Это самый точный ответ на его вопрос №5. Он собирался писать 300 строк рендера формы из JSON — вот эти 300 строк, только их 536 КБ, они MIT, отлажены на тысячах проектов и покрывают массивы и вложенность, до которых самописный вариант доберётся месяца через два. Кладётся в static/, работает офлайн, новых pip-пакетов ноль, установщик не трогается. Схему справочника под конкретного клиента хранит в SQLite как TEXT, форма собирается сама. Ограничение честное: JSON Schema — это про ДАННЫЕ, а не про layout, так что тонко управлять расположением полей неудобно (есть format/options, но это не полноценная вёрстка); если клиенту нужен красивый многоколоночный бланк — либо Amis, либо руками.

**Трудоёмкость:** день

## formio.js — MIT
https://github.com/formio/formio.js

**Что:** Рендерер форм по JSON-описанию плюс — и это главное — визуальный drag-and-drop конструктор форм, оба в одной MIT-библиотеке, подключаются тегом script.

**Умный приём:** Открытая часть включает не только Formio.createForm(element, schemaJSON), но и Formio.builder(element, {}, {}) — полноценный конструктор с палитрой компонентов, перетаскиванием, настройкой валидации и условной логики. На выходе он отдаёт тот самый JSON, который потом скармливается рендереру. То есть цикл «нарисовал форму мышкой → сохранил JSON → форма работает» замыкается целиком в браузере, без бэкенда и без облака form.io.

**Применимо:** Это меняет его бизнес-модель, а не только код. Сейчас «у каждого клиента свои справочники и формы» = он едет, разбирается, кодит. С конструктором он на внедрении даёт делопроизводителю заказчика экран «соберите свою форму», тот собирает сам, JSON падает в SQLite — и правка формы через полгода не требует его приезда и релиза. Для бутикового внедрения на переиспользуемом ядре это ровно тот рычаг, который он ищет. Минусы: библиотека тяжелее json-editor, тянет много встроенных стилей (заточена под Bootstrap), и её условная логика на больших формах умеет тормозить. Проверять надо на его реальной путевом листе, а не на демо.

**Трудоёмкость:** неделя

## Django Admin — BSD-3-Clause
https://docs.djangoproject.com/en/stable/ref/contrib/admin/

**Что:** Эталон жанра: по моделям БД автоматически строит полноценный раздел администрирования — списки с фильтрами, поиском, сортировкой, формы создания/редактирования, права доступа. Серверный рендер на шаблонах, никакой сборки.

**Умный приём:** Самое ценное — не автогенерация, а ДЕКЛАРАТИВНОЕ ПЕРЕОПРЕДЕЛЕНИЕ. Экран описывается одним классом из плоских атрибутов: list_display, list_filter, search_fields, readonly_fields, list_editable, fieldsets (группировка полей в блоки), inlines (дочерние записи прямо в форме родителя), actions (массовые операции над отмеченными строками). Автогенерация даёт 70% бесплатно, а оставшиеся 30% донастраиваются построчно, БЕЗ выпадения в «ну ладно, пишу страницу руками». Именно это отличает живой генератор от игрушечного — и именно на этом ломаются почти все остальные: как только задача выходит за плоский CRUD (вычисляемая колонка, две связанные таблицы на одном экране, кнопка «провести документ»), генератор без такого слоя переопределений выкидывает тебя в ручной код целиком.

**Применимо:** Django ему не нужен и не подходит (у него FastAPI и SQLite без ORM), но ЭТУ структуру надо скопировать один в один. Пусть каждый справочник клиента описывается одним питоновским словарём: {"table": "contractors", "title": "Контрагенты", "list_display": [...], "search_fields": [...], "fieldsets": [...], "actions": [...]}. Один generic-роутер на FastAPI читает словарь, строит SQL к сырому SQLite и отдаёт JSON; один generic-шаблон (или Amis/json-editor) рисует экран. Новый справочник = новый словарь на 15 строк вместо недели. И сразу закладывай слой переопределений — иначе на третьем клиенте упрёшься. Заодно посмотри inlines и actions: путевые листы — это как раз документ с табличной частью, то есть inline в чистом виде.

**Трудоёмкость:** неделя

## sqladmin — BSD-3-Clause
https://github.com/smithyhq/sqladmin

**Что:** Админка для FastAPI/Starlette на SQLAlchemy: Admin(app, engine) + классы ModelView, интерфейс на Jinja2-шаблонах со стилями Tabler. 2.8k звёзд, активный (пуш август 2026). Репозиторий переехал с aminalaee/sqladmin на smithyhq/sqladmin.

**Умный приём:** Монтируется как саб-приложение в УЖЕ РАБОТАЮЩИЙ FastAPI — не отдельный сервис, не отдельный порт, не отдельный процесс. Минимум кода буквально такой:

admin = Admin(app, engine)
class UserAdmin(ModelView, model=User):
    column_list = [User.id, User.name]
admin.add_view(UserAdmin)

Весь фронт — серверные Jinja-шаблоны, Node не нужен ни при разработке, ни при установке. SQLite поддержан явно (в quickstart прямо sqlite:///example.db). Стоит прочитать исходники его шаблонов list.html/details.html — это готовый рабочий образец «как отрисовать любую таблицу одним шаблоном с сортировкой, поиском и пагинацией», и он на Jinja, который у него и так есть.

**Применимо:** Как готовая библиотека — с оговоркой: требует SQLAlchemy-модели, а у него SQLite без ORM. Тащить SQLAlchemy ради админки я бы не стал (лишняя зависимость в хрупкий установщик, плюс переписывание слоя данных). Но: (а) это лучший в списке образец кода для копирования — BSD-3 разрешает брать куски с указанием авторства; (б) если в каком-то клиентском проекте он всё-таки заведёт SQLAlchemy, sqladmin даёт полную админку за час. Практический шаг на завтра — вычитать его шаблоны и структуру ModelView, и сделать свой аналог поверх сырых SQL-запросов.

**Трудоёмкость:** неделя

## Piccolo Admin — MIT
https://github.com/piccolo-orm/piccolo_admin

**Что:** Веб-админка над ORM Piccolo: фронт на Vue, бэк — REST на ASGI. 468 звёзд, живой (пуш июнь 2026). Piccolo ставится с драйвером SQLite: pip install 'piccolo[sqlite]'.

**Умный приём:** Два приёма. Первый — СОБРАННЫЙ ФРОНТ ЛЕЖИТ ВНУТРИ PYPI-ПАКЕТА. При pip install ты получаешь готовые JS/CSS, Node на машине не нужен вообще. Это правильный ответ на «фреймворк на Vue/React, но пользователю сборка не нужна», и ровно так стоит паковать его собственные экраны, если он когда-нибудь захочет что-то тяжелее ваниллы. Второй — механизм custom forms: регистрируешь Pydantic-модель + функцию-обработчик, и в админке появляется отдельная страница-форма, никак не привязанная к таблице БД. То есть разовые нетабличные экраны («сформировать отчёт за период», «пересчитать нормативы») не выпадают из системы и не требуют ручной вёрстки.

**Применимо:** Сама админка — вряд ли: Piccolo ORM он не использует, а тянуть новую ORM ради неё нет смысла. Применимы обе идеи по отдельности, и вторая прямо сегодня: у него ведь ровно такая структура задач — часть экранов это справочники (CRUD), а часть это ДЕЙСТВИЯ (проверить документ, сгенерировать письмо, пакетная проверка). Заведи в своём decl-описании второй тип экрана — «форма-действие»: список полей + имя серверного обработчика + что делать с результатом. Тогда и справочники, и кнопки клиента описываются одним и тем же механизмом, а не двумя разными кусками кода.

**Трудоёмкость:** день

## Flask-AppBuilder — BSD-3-Clause
https://github.com/dpgaspar/Flask-AppBuilder

**Что:** Фреймворк быстрой разработки поверх Flask: автогенерация CRUD по моделям, встроенная система прав, графики. Jinja2 + Bootstrap, без Node. 5k звёзд, активный (пуш июль 2026). На нём построен Apache Superset — то есть на масштабе проверен.

**Умный приём:** Права доступа генерируются ВМЕСТЕ с экраном. Объявил ModelView — фреймворк автоматически завёл пермишены can_list/can_show/can_add/can_edit/can_delete на этот вид и положил их в БД, дальше роли раздаются через UI. Не нужно ни писать проверки в каждом хендлере, ни поддерживать отдельный список прав, который вечно отстаёт от списка экранов. Второй приём — иерархия базовых классов (BaseView → SimpleFormView → ModelView), где generic-экран это частный случай ручного: если стандартного вида не хватает, наследуешься уровнем ниже и пишешь свой метод, не выходя из системы навигации, прав и шаблонов.

**Применимо:** Flask вместо FastAPI — переезжать не надо. Забирать надо связку «декларация экрана порождает права». У него 30 пользователей в ПожСервисе, а при следующем клиенте почти наверняка встанет вопрос «кладовщик не должен видеть договоры». Если права привязать к тому же словарю, что описывает экран, это ноль дополнительной работы на каждого нового клиента; если делать отдельно — это будет отдельная неделя на каждом внедрении. Заложи в decl-схему поле roles/permissions СРАЗУ, даже если пока все админы — потом дописать будет вчетверо дороже.

**Трудоёмкость:** день

## Appsmith — Apache-2.0
https://github.com/appsmithorg/appsmith

**Что:** Полноценная платформа внутренних инструментов: перетаскиваешь виджеты на холст, привязываешь к запросам в 25+ источников данных. 40.6k звёзд, самый популярный в категории.

**Умный приём:** Модель реактивных биндингов. Виджет не «получает данные» кодом — в его свойство пишется выражение {{ getUsers.data }}, и Appsmith сам строит граф зависимостей: изменился результат запроса — перерисовались все виджеты, которые на него ссылаются; изменилось значение в поле — пересчитались формулы, которые его читают. Это заметно мощнее статической JSON-схемы: одним выражением связываются таблица и форма («форма показывает {{ table.selectedRow }}»), и такие связки как раз составляют 80% реальных внутренних экранов.

**Применимо:** Сама платформа — категорически нет: официальный self-host это Docker со встроенными MongoDB, Redis и PostgreSQL внутри контейнера и минимум 8 ГБ RAM на хост. Все четыре пункта — из его списка запретов. Но идею биндингов стоит подсмотреть и упростить до предела: в его decl-схеме разрешить в свойствах строки вида "${selected.id}" и "${form.contractor_id}", а на клиенте написать примитивный резолвер (~40 строк) — этого хватит, чтобы связать список и карточку без единой строки JS на каждом экране. ## Directus — MSCL (source-available, переходит в GPLv3 через 4 года) — НЕ open source

## Baserow — MIT (ядро) + проприетарная premium/enterprise часть
https://github.com/baserow/baserow

**Что:** No-code база данных на Django + Vue (Nuxt 3) + PostgreSQL, альтернатива Airtable. 5.5k звёзд, очень активный. Единственный в списке, написанный на Python — потому и стоит посмотреть код.

## Tabulator — MIT
https://github.com/olifolkerd/tabulator

**Что:** Интерактивная таблица на чистом JS: подключается одним тегом script, конфигурируется одним объектом — колонки, сортировка, фильтры, редактирование ячеек на месте, группировка, экспорт в CSV/XLSX, виртуальный скролл на десятках тысяч строк.

Дальше новый справочник клиента — это 15 строк конфига, а не неделя.

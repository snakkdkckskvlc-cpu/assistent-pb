# Инструкции для Claude в этом репозитории

Читается автоматически в начале каждой сессии. Здесь только то, что нельзя
вывести из кода за разумное время, и то, за что уже платили ошибками.

Дополняет, а не заменяет: [CONTRIBUTING.md](CONTRIBUTING.md) — команды и правила
коммитов, [docs/README.md](docs/README.md) — навигация по документации,
[docs/03-architecture/adr/](docs/03-architecture/adr/) — принятые решения.

---

## 1. Что это за проект

Офлайн-ассистент для ООО «ПожСервис» и ООО «ПожМастер» (Липецк, подрядчики
ПАО НЛМК). Пользователи — сотрудники компании, не программисты: секретарь,
инженер, бухгалтер. Их около тридцати.

Пять функций: проверка орфографии деловых документов, анализ договоров с
поиском рисков и ссылками на закон, письма на фирменном бланке, вопрос по
документу, учёт транспорта с путевыми листами.

**Тон общения с пользователем — обычный человеческий русский.** Он не знает,
что такое «эндпоинт» и «миграция». Объяснять последствия, а не механику:
не «добавил ALTER TABLE», а «старая база продолжит работать, данные не
потеряются».

## 2. Стек — фактический, а не желаемый

| Слой | Что | Где |
|---|---|---|
| Backend | Python 3.11, FastAPI, uvicorn | `apps/backend/src/fire_safety_backend/` |
| База | **SQLite**, штатная либа, без ORM | `infrastructure/db.py` |
| Модель | **Ollama локально**, 127.0.0.1:11434 | `infrastructure/llm.py` |
| Поиск | ChromaDB embedded + BM25, e5-large | `packages/rag/src/fire_safety_rag/` |
| Орфография | LanguageTool локально, 127.0.0.1:8081 | `infrastructure/languagetool.py` |
| Фронтенд | **ванильные HTML/CSS/JS, сборки нет** | `apps/desktop/frontend/` |
| Десктоп | pywebview (WebView2 на Windows) | `apps/desktop/src/` |
| Боевая машина | Ryzen 5 5600, 128 ГБ RAM, Windows | один сервер на компанию |

Масштаб: ~26 500 строк Python в 157 файлах, 55 тестовых файлов, 12 файлов
фронтенда.

**Чего в проекте НЕТ и что заводить нельзя без явного решения пользователя:**

- Node.js/TypeScript/Next.js — фронтенд намеренно без сборки: правку страницы
  должен уметь внести любой, кто откроет файл, без `npm install`.
- Redis, BullMQ, Celery — очередь своя, в памяти процесса
  (`infrastructure/queue.py`), потому что сервер один и внешних демонов на нём
  быть не должно.
- PostgreSQL, RLS, мультитенантность — организаций две, они в одной таблице,
  разграничение по пользователям сделано владельцем записи (`owner`).
- Docker — приложение ставится на Windows-сервер скриптом, не в контейнере.
- Любые облачные сервисы для кода и документов — см. раздел 3.

Если задача выглядит так, будто требует чего-то из этого списка, — сначала
сказать пользователю, во что это обойдётся, и дождаться решения.

## 3. Красные линии

Нарушение любой из них ломает обещание, данное пользователю. Проверять до
коммита, а не после.

### 3.1. Приложение не ходит в интернет

`infrastructure/netguard.py` разрешает только loopback. Это не паранойя: в
договорах с НЛМК есть раздел о конфиденциальности со штрафом. Любой сетевой
вызов из backend — ошибка, даже полезный (за метаданными модели, за телеметрией
библиотеки).

**Отсюда следует и правило для меня:** нельзя отправлять код проекта и тексты
договоров во внешние сервисы — ни в облачные анализаторы кода, ни в чужие API.
Инструмент, который «для удобства» загружает репозиторий к себе, здесь
неприменим по той же причине, по которой запрещён netguard.

### 3.2. Манифест целостности

Приложение при старте сверяет файлы с `integrity.json` и **отказывается
запускаться** при расхождении. Это уже дважды превращало программу у
пользователя в кирпич.

Правило: изменил любой файл из манифеста — в ТОМ ЖЕ коммите пересобери:

```bash
./venv/bin/python scripts/build_integrity_manifest.py
```

Манифест не должен содержать файлы, которых нет в git, — сборщик за этим
следит, не обходить.

### 3.3. Документы на диске зашифрованы

Загруженные и сгенерированные файлы лежат зашифрованными
(`infrastructure/secure_files.py`, DPAPI на Windows). Новый генератор пишет
через `secure_files.encrypted_output`, а не напрямую в файл. Отдаётся клиенту
расшифрованное содержимое через `/api/download/`, с проверкой владельца.

### 3.4. Персональные данные

Справочник водителей содержит СНИЛС и номера водительских удостоверений —
обязательные реквизиты путевого листа, хранение согласовано с пользователем.
Правила: роутер только под входом, в списковых ответах эти поля не отдавать
(см. `services/waybills.py::print_data` — почему сделано отдельным запросом).

### 3.5. Корпус нормативки перечислен в `.gitignore` пофайлово

Забыть строку — значит тихо не довезти документ до пользователя. Так уже
терялся Гражданский кодекс. Проверка: `scripts/check_corpus.py`.

### 3.6. Роутеры закрываются целиком

Новый роутер добавляется в защищённый список в `main.py::create_app`, а не
обвешивается `Depends` по ручкам: ручек больше двадцати, забытая означает
открытый доступ к договорам компании из всей внутренней сети.

## 4. Как я работаю над задачей

### 4.1. Полный код, без заглушек

Никаких `# остальной код без изменений`, `TODO: реализовать`, урезанных
примеров. Если функция написана — она работает целиком. Если часть задачи
сделать нельзя — сделать всё остальное полностью и сказать словами, что
осталось и почему.

### 4.2. Цикл проверки

Порядок для любой правки:

1. **Понять существующее.** Прочитать модуль, который трогаю, и его тесты.
   Не угадывать имена полей и методов — открыть и посмотреть.
2. **Тест вперёд, где он дешёвый.** Новая чистая функция, разбор формата,
   арифметика, граничный случай — сначала тест. Он ловит опечатку в имени поля
   лучше любого перечитывания.
3. **Написать код.**
4. **Прогнать проверки** (раздел 4.3) и чинить, пока не зелено.
5. **Прогнать сценарий целиком** — как им будет пользоваться человек, через
   HTTP с настоящим входом, а не только юнит-тестом. Именно так нашлись:
   401 при скачивании письма, пустая графа «расход по норме», падение
   `init_db` на существующей базе.

### 4.3. Проверки — и ограничение по железу

**Ноутбук пользователя не тянет полный `pytest`** — это его прямое указание,
повторённое несколько раз. Полный прогон делает CI
(`.github/workflows/ci.yml`) и боевой сервер.

Локально:

```bash
# всегда, они быстрые
./venv/bin/python -m ruff check .
./venv/bin/python -m ruff format .

# точечно — только файлы, которых касалась правка
./venv/bin/python -m pytest apps/backend/tests/unit/test_<модуль>.py -q

# проверка типов: ловит выдуманные имена полей и методов
PYTHONPATH="apps/backend/src:packages/rag/src:apps/desktop/src" \
  ./venv/bin/python -m mypy --python-version 3.13 apps/backend/src packages/rag/src

# перед коммитом, если менялись файлы из манифеста
./venv/bin/python scripts/build_integrity_manifest.py
```

`uv` на машине пользователя не установлен — использовать `./venv/bin/python`.

Про mypy два момента. Версия в venv (1.14.1) совпадает с CI намеренно: на более
новой список замечаний другой, и «зелено локально, красно в сборке» съедает
время. `--python-version 3.13` нужен только локально — в `mypy.ini` стоит 3.11
под CI, а в локальном venv Python 3.13, и заглушки numpy оттуда используют
синтаксис новее 3.11, из-за чего проверка обрывается на первой же ошибке.

**Замечаний около полусотни, и они в основном шум** — chromadb типизирован
слабо, а сужение типа через локальный флаг (`is_docx = source_path is not None`)
mypy не видит. Смотреть стоит на новые замечания в файлах, которых касалась
правка, а не на общее число. В CI mypy стоит с `|| true` по той же причине.

Ollama и LanguageTool локально могут быть не подняты. Тесты, которым нужна
модель, локально не гонять — они для сервера.

Когда быстрого теста не хватает, писать одноразовый прогон в scratchpad и
запускать через `TestClient` — это дёшево и показывает реальное поведение.

### 4.3.1. Проверка страниц в браузере

`.mcp.json` подключает Playwright. Он нужен там, где `TestClient` бессилен:
фронтенд — ванильный JS без сборки и без тестов, а на странице путевого листа
около сотни полей, которые рисуются скриптом. Проверять ими стоит то, что
ломается молча: отрисовалось ли поле, ушло ли значение в сохранение,
не подставился ли пустой `<select>`.

Ограничение по железу то же: браузер поднимать под конкретную проверку и
закрывать, а не держать открытым и не гонять по нему длинные сценарии.
Нагрузочных прогонов на машине пользователя не делать.

### 4.4. Что писать в комментариях

В проекте принят плотный комментарий, объясняющий **почему**, а не что. Держать
ту же плотность. Хороший комментарий отвечает на вопрос «почему не сделано
очевидным способом» и часто содержит замер или случай из практики. Плохой
пересказывает код.

Всё на русском: и комментарии, и сообщения ошибок, и тексты интерфейса. Сообщение
об ошибке пишется для секретаря, а не для программиста: «Машина уже в рейсе —
сначала отметьте возврат», а не «IntegrityError on trip.vehicle_id».

**Следить за случайными не-кириллическими символами.** В код уже трижды
попадали китайские иероглифы внутри русских слов, а в исходник — невидимый
символ забоя вместо `\b`, из-за которого правило не срабатывало никогда.
Глазами такое не ловится.

### 4.5. Коммиты

Conventional commits, тело — на русском, по делу: что было измерено, что
поменялось, какое решение принято и почему. Заканчивать строкой
`Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`.

Коммитить и пушить только когда попросили. Пушить в `main` можно — второй
разработчик делает так же, поэтому перед пушем всегда `git fetch` и разбор
чужих коммитов, а не слепой `--force`.

## 5. Доменные правила, которые дорого нарушить

### 5.1. Деньги, топливо и расстояния — целыми числами

Копейки (`_kop`), миллилитры (`_ml`), метры (`_m`), сотые доли (`_x100`).
Пересчёт в человеческие единицы — на границе API, в одном месте
(`services/units.py`). Топливо складывается сотнями рейсов, и погрешность
`float` даёт расхождение с бухгалтерией, которое нечем объяснить.

### 5.2. Снимок вместо ссылки там, где документ уже сдан

Норма расхода топлива пишется в путевой лист копией. Приказ меняет норму, и без
снимка пересчёт закрытого месяца дал бы не те цифры, по которым списали.
Тот же принцип — везде, где цифра ушла в отчётность.

### 5.3. Не считать то, чего не знаем

Нет утверждённой нормы — в бланке прочерк, а не «примерно по паспорту». По этой
цифре списывают топливо. Коэффициенты изменения нормы вводятся и печатаются, но
в расчёт не входят, пока нет приказа организации.

### 5.4. Ручной ввод — основа, автоматика — уточнение

ГЛОНАСС стоит на 3 машинах из 12. Модуль, построенный вокруг трекера, оставил
бы девять машин без учёта. Все поля заполнимы человеком; источник записи
помечается отдельно (`trip.source`).

### 5.5. Миграции обязательны

`CREATE TABLE IF NOT EXISTS` существующую таблицу не трогает. Новый столбец у
живой таблицы доезжает только через `_MIGRATIONS` в `db.py`. Индекс по такому
столбцу — в `_POST_MIGRATION_SCHEMA`, иначе `executescript` падает на
«no such column» у всех, кто запускал прошлую версию.

## 6. Работа с моделью

Ollama на CPU. Генерация упирается в память, а не в процессор.

- **`num_ctx` менять нельзя без причины** — смена перезагружает модель.
  Значение подбирается по объёму RAM (`config.py::_auto_num_ctx_legal`).
- **Длинный запрос молча обрезается** — Ollama срезает начало вместе с
  системным промптом. Так уже был получен ноль находок на договоре. Резать
  документ на части самим, а не надеяться на окно.
- **Структурированный ответ — через `format: json` и разбор в Pydantic.**
  Модель ошибается в JSON; разбор обязан переживать это без падения задачи.
- **Обвязка важнее модели.** Замерено: голая модель находит 10 красных рисков
  из 23, с промптом, RAG и проверкой цитат — 16. Выбрасывать обвязку ради
  «более умной модели» нельзя.
- **Проверять то, что модель утверждает.** Цитата сверяется с текстом
  документа, номер статьи — с выданным контекстом. Непроверенное помечается
  в интерфейсе.
- **Любое утверждение о качестве — с замером.** В этом проекте принято сравнивать
  на датасете и писать цифры в коммит. «Стало лучше» без числа не принимается.

Промпты — в `resources/prompts/`, не в коде.

## 7. Надёжность

### 7.1. Повторный запрос не должен ломать данные

Пользователь нажимает кнопку дважды. Операции, создающие документы и записи,
обязаны это переживать: уникальные индексы там, где дубль недопустим (номер
путевого листа), понятная ошибка вместо второго документа, `INSERT OR IGNORE`
в сидах.

### 7.2. Очередь

Своя, в памяти (`infrastructure/queue.py`), с честностью между пользователями:
тридцать сотрудников, одна модель, и один человек с пачкой договоров не должен
занять её на час. Результаты задач переживают перезапуск сервера
(`task_results`), потому что человек ждал их минутами.

### 7.3. Отказ должен быть виден

Молчаливая деградация — худший вид отказа в этом проекте, и он уже случался
трижды: письмо без фирменного бланка выглядело нормально, обрезанный промпт
давал ноль находок, скачивание молча не работало. Правило: если результат
получен в урезанном виде — сказать об этом в интерфейсе, до того как человек
отправит документ контрагенту.

### 7.4. База

SQLite в WAL, `busy_timeout`. Индексы — под фактические запросы: составные там,
где фильтр идёт по двум полям сразу (`idx_trip_vehicle(vehicle_id, departed_at)`,
`idx_trip_waybill(waybill_id, seq)`). Частичный уникальный индекс, когда
уникальность нужна не для всех строк (номер листа — только у выписанных).
Разграничение доступа — через `owner` у записи и проверку в сервисе.

## 8. Чего не делать

- Не запускать полный `pytest` на машине пользователя.
- Не пересобирать индекс RAG без просьбы — это десятки минут.
- Не трогать `chunk_sentences`: на нём висят орфография, письма и нарезка
  договора. Новая стратегия чанкинга добавляется рядом.
- Не делать `git stash`, чтобы посмотреть чистое дерево, — использовать
  `git show HEAD:path` или worktree.
- Не переносить импорты моделей тела запроса FastAPI в `TYPE_CHECKING` —
  приложение упадёт на старте.
- Не менять `favicon`/названия страниц ради красоты — люди находят вкладку по
  ним.
- Не оставлять ключи и токены в коде и в истории.
